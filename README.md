# Jarvis — что было исправлено

## 1. Главный баг: VAD не видел речь (SileroVAD.cpp / .h)

Модель `silero_vad.onnx` — это Silero VAD v5. Официальная реализация подаёт
на вход не 512 сэмплов, а **576 = 64 (контекст от предыдущего кадра) + 512
(новый кадр)**. Старый код кормил модель голыми 512 сэмплами без контекста.
Модель не падала (входной тензор объявлен с динамической формой), но
вероятность речи почти никогда не поднималась выше 0.1–0.15 — то есть порог
`VAD_SPEECH_THRESHOLD = 0.55` не пробивался почти никогда, даже на громкой
чистой речи.

Проверено на скомпилированном коде: на тестовой фразе `max_prob` было
`0.114` (без контекста) против `0.9999` (с контекстом).

Исправлено в `core/include/SileroVAD.h` и `core/src/SileroVAD.cpp`.

## 2. RUNPATH был захардкожен на машину сборки

Бинарник помнил абсолютный путь `/home/.../onnxruntime.../lib`, из-за чего
при переносе/переименовании папки переставал находить `libonnxruntime.so`.
Теперь путь в `core/CMakeLists.txt` задан через `$ORIGIN` — переезжает
вместе с папкой проекта.

## 3. Запись микрофона могла тормозиться сетью (main.cpp)

Раньше `zmq_socket.send()` вызывался прямо в цикле чтения микрофона. Если
Python был занят распознаванием предыдущей фразы, а пользователь уже
начинал новую (перебивание), при заполнении внутренней очереди ZMQ `send()`
мог заблокироваться — и мы бы теряли аудио. Теперь отправка вынесена в
отдельный поток (`core/include/PhraseSender.h`) с очередью: запись с
микрофона никогда не ждёт сеть.

## 4. Начало фразы обрезалось (main.cpp)

VAD распознаёт речь не мгновенно — ему нужно 2–3 кадра (60–90 мс), чтобы
"разогнаться" выше порога. Раньше запись фразы начиналась только с кадра,
на котором сработал VAD, и начало слова "Джарвис" часто терялось. Добавлен
pre-roll буфер (~320 мс, кольцевой), который приклеивается к фразе в момент
срабатывания VAD.

## 5. Защита от зависшей фразы

Если VAD ложно держится "в речи" (шум, гул) — раньше буфер рос бы вечно.
Теперь есть `MAX_PHRASE_SAMPLES` (15 сек) — по достижении фраза
принудительно уходит на распознавание, а запись продолжается как ни в чём
не бывало (это же покрывает и сценарий, когда человек говорит длинно без
пауз, перебивая сам себя).

## 6. Python-сервер падал целиком при ошибке на одной фразе (server.py)

Раньше весь `try/except` был вокруг всего цикла — одна битая фраза
(например, если Whisper споткнулся) убивала сервер, и дальше он вообще
переставал что-либо принимать. Теперь приём аудио (`socket_audio.recv()`) и
распознавание (Whisper) разнесены на два потока через `queue.Queue`, и
ошибка на одной фразе не мешает обработке следующих.

## 7. "Диалоговое окно" — не нужно повторять "Джарвис" каждый раз

После того как сказано слово-активатор, в течение 10 секунд (см.
`ACTIVE_WINDOW_SECONDS` в `server.py`) следующие фразы считаются командами
без повторного "Джарвис" — как у обычных голосовых ассистентов. Это и есть
базовая обработка "перебивания"/продолжения диалога.

## 8. requirements.txt был неполным

Не хватало `faster-whisper`, `rapidfuzz`, `PySide6` — только `pyzmq`.
Исправлено.

# Раунд 2: закрытые сценарии из чек-листа (акустика/железо/сессии)

Список сценариев был разобран на 3 корзины: (1) чинится на уровне
VAD/STT/сессий, (2) принципиально требует LLM/NLU, (3) требует железа
(TTS+AEC, второе устройство). Ниже — что сделано по корзине (1), с проверкой
на реально скомпилированном коде и живым end-to-end тестом (python-клиент,
эмулирующий протокол C++ ядра → server.py → UI-сокет).

- **Импульсный шум / щелчок (хлопок двери, лай, щелчок аппаратуры)** —
  `main.cpp`: добавлен антидребезг открытия фразы (`CONFIRM_FRAMES = 2`,
  ~64мс). Одиночный кадр с высокой вероятностью речи больше не открывает
  фразу — нужно 2 кадра подряд. Начало реальной речи по-прежнему не
  обрезается благодаря pre-roll буферу.
- **Галлюцинации тишины/шума в STT** — `server.py`: добавлен
  `is_hallucinated_segment()` — отсекает сегменты по `no_speech_prob`,
  `avg_logprob`, `compression_ratio` (штатные признаки "выдумывания" у
  Whisper). Проверено сценарием: шумовая фраза с плохими метриками
  корректно не долетает до UI.
- **"Зависла STT, ответ пришёл после того как сессия уже закрылась по
  таймауту"** — раньше диалоговое окно проверялось по текущему времени
  (когда Whisper закончил), теперь — по времени, когда фраза реально была
  произнесена (`ts` в заголовке сообщения). Долгая обработка одной фразы
  больше не путает логику "продолжается диалог или нет".
- **Мышление вслух / долгая пауза с "эээ" в середине фразы** — уже
  работало (любой звук выше порога сбрасывает счётчик тишины), но hangover
  увеличен с ~0.8с до ~1.0с для небольшого запаса.
- **Тихий шёпот** — расширен диапазон авто-гейна (порог активации снижен
  со 100 до 50, потолок усиления поднят с 10x до 15x). Это не чинит
  физически "глухой" микрофон, но даёт больше шансов тихой речи.
- **Сетевая устойчивость / порядок фраз** — каждая фраза теперь уходит
  двумя zmq-фреймами: JSON-заголовок `{"seq", "ts"}` + сырые PCM16-байты.
  Это база для будущего сетевого сценария (не только localhost) и для
  честного лога задержки речь→текст.

Корзины (2) и (3) намеренно не тронуты — это LLM/NLU-слой (не построен
командой линии VAD-порогов) и железо (TTS+AEC, второе устройство), которых
в проекте пока физически нет.

# Раунд 3: повторный аудит (архитектура/баги)

По запросу "всё ли оптимально" — прошёлся по коду ещё раз пристрастно,
специально ища то, что сам мог упустить в спешке. Нашлось 4 реальные вещи:

1. **Дублирование кадра на стыке открытия фразы (main.cpp)** — при
   срабатывании антидребезга (раунд 2) preroll-буфер уже содержал текущий
   кадр, а следом он же добавлялся ещё раз общей веткой записи. На каждой
   фразе в начало записи попадали лишние ~32мс повторяющегося звука.
   Проверено отдельным тестом на симуляции состояний: раньше кадр
   дублировался бы, теперь каждый кадр входит в буфер ровно один раз.
2. **Неограниченный рост очереди в PhraseSender.h** — если Python-сервер
   долго недоступен (упал/не запущен), очередь на отправку росла бы
   бесконечно. Добавлен потолок в 50 фраз с вытеснением самых старых
   (свежая речь важнее устаревшего бэклога).
3. **CMakeLists.txt собирал без оптимизаций по умолчанию** — `cmake ..` без
   явного `-DCMAKE_BUILD_TYPE=Release` собирал в дефолтном (не оптимизированном)
   режиме. Теперь Release выставляется по умолчанию, если не указано иное.
4. **Двойная инициализация PortAudio (AudioRecorder.cpp)** — при
   использовании `deviceNameHint` (сейчас неактивный путь, т.к. `Start()`
   вызывается без аргументов) `Pa_Initialize()` вызывался дважды, а
   `Pa_Terminate()` в `Stop()` — один раз. Не проявлялось в текущем сценарии
   использования, но было заложенной миной на будущее. Исправлено.

Также зафиксированы (не исправлены — это либо косметика, либо territория
LLM-слоя, а не VAD/аудио):
- `strip_wake_word()` не отрежет имя, если STT склеил его с командой без
  пробела ("джарвисвыключисвет") — это уже вопрос сегментации слов, решается
  нормально только на уровне LLM/NLU, не VAD.
- Сообщение "[ZMQ] Успешно подключено!" при старте ядра технически означает
  только "сокет создан", а не "Python точно слушает" — `zmq_socket.connect()`
  всегда возвращает успех сразу же, реальное соединение асинхронное. На
  поведение это не влияет (ZMQ переподключается и буферизует сам), но как
  формулировка немного вводит в заблуждение.

# Этап 1: LLM-слой (через OpenRouter, OpenAI-совместимый протокол)

Распознанный текст команды больше не уходит в UI как есть — сначала идёт в
`agents.DialogManager`, который обращается к LLM с function calling, и уже
осмысленный ответ модели уходит в UI.

**Почему OpenRouter, а не провайдер напрямую:** один ключ и один эндпоинт
дают доступ к десяткам моделей (Gemini, DeepSeek, Llama, Qwen и т.д.), часть
из них бесплатна. Код написан под универсальный OpenAI-совместимый протокол,
поэтому провайдера/модель можно сменить одной переменной окружения, без
переписывания кода — включая переход на прямой DeepSeek или локальный Ollama
позже.

## Настройка

1. Зарегистрируйся на https://openrouter.ai и возьми ключ на
   https://openrouter.ai/keys
2. Установи переменные окружения перед запуском `server.py`:
   ```bash
   export LLM_API_KEY="sk-or-..."
   # Необязательно - по умолчанию google/gemini-2.5-flash через OpenRouter:
   export LLM_MODEL="google/gemini-2.5-flash"
   ```
3. **Про бесплатные модели**: список `:free`-моделей на OpenRouter меняется
   буквально каждый месяц (проверено на нескольких независимых источниках в
   июле 2026 — списки расходятся даже между свежими статьями). Не полагайся
   на конкретный `:free`-id из любого гайда, включая этот — смотри актуальный
   живой список на https://openrouter.ai/models?max_price=0 и подставляй
   нужный id в `LLM_MODEL`.
4. Если `LLM_API_KEY` не задан — сервер **не падает**, а печатает
   предупреждение и работает в режиме чистого STT-эхо (как на предыдущих
   этапах). LLM-слой — опциональная надстройка, а не обязательное условие
   запуска.

## Архитектура

- `framework/agents/tools.py` — инструменты (function calling):
  `get_current_datetime()` и `calculate(expression)`, плюс их JSON-схемы в
  формате OpenAI `tools`. В отличие от Gemini SDK, OpenAI-совместимый
  протокол не строит схему автоматически и не выполняет вызов сам — схему
  описываем руками, вызов выполняем руками в `dialog_manager.py`. Дороже в
  коде, зато одинаково работает с любым провайдером через OpenRouter.
- `calculate()` намеренно не использует `eval()` — выражение приходит от
  LLM, которая реагирует на текст от пользователя, а `eval()` дал бы прямой
  путь к инъекции произвольного Python-кода через промпт. Вместо этого —
  разбор через `ast` с разрешённым белым списком операций. Проверено
  конкретными эксплойтами (`__import__(...)`, `open(...)`) — оба отбиваются.
- `framework/agents/llm_client.py` — создаёт OpenAI-совместимый клиент из
  переменных окружения (`LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`). Чтобы
  переключиться на прямой DeepSeek или локальный Ollama — не трогаем код,
  просто меняем `LLM_BASE_URL`/`LLM_MODEL`/`LLM_API_KEY`.
- `framework/agents/dialog_manager.py` — `DialogManager.handle(text) -> str`.
  Ручной цикл tool-calling (до `MAX_TOOL_HOPS` кругов): модель просит вызвать
  функцию → мы вызываем → результат уходит обратно → модель либо просит ещё
  один вызов, либо отвечает текстом. Хранит историю разговора, обрезает её
  сверху ЦЕЛЫМИ ходами (`HISTORY_MAX_TURNS`) — обрезка никогда не разрывает
  `tool_call` и его `tool`-ответ посередине (это сломало бы протокол).
  `reset()` вызывается сервером при новой сессии (сказано "Джарвис" после
  долгой паузы) — старый контекст не тащится в новый разговор.
- При сетевой ошибке / таймауте / исчерпанной квоте `handle()` не бросает
  исключение — возвращает вежливый текст об ошибке и откатывает историю.

DeepSeek для тяжёлых/код-задач в этом этапе ещё не подключён (следующий
этап — отдельный `delegate_to_deepseek`-инструмент, который дёргает другую
модель через тот же OpenRouter-клиент, просто с другим `model=`).

## Что проверено (без реального обращения к LLM — ключа и доступа к
`openrouter.ai` в песочнице нет, поэтому это mock-тесты и одна честная
оговорка):

- Реальный установленный `openai` SDK (2.48.0) — сигнатура
  `chat.completions.create` подтверждена интроспекцией установленного пакета,
  не по памяти.
- `calculate()`/`get_current_datetime()` — юнит-тесты, включая 2 попытки
  инъекции кода (отбиты).
- `DialogManager` — мок-тест на подставном `OpenAI`-клиенте: полный цикл
  tool-calling (запрос инструмента → реальное выполнение → второй запрос →
  финальный текст), корректный откат истории при сетевой ошибке, и обрезка
  истории на 20 ходах подряд — история всегда обрезается по границе `user`,
  никогда не разрывая `tool_call`/`tool`-ответ.
- Полный путь целиком: фейковая фраза → `server.py` → заглушка Whisper →
  `DialogManager` (с моком LLM, который решает вызвать `calculate`) →
  реальное выполнение инструмента → ответ в UI-сокете.
- **Не проверено**: реальный сетевой вызов к OpenRouter с настоящим ключом —
  сеть до `openrouter.ai` в этой песочнице недоступна, проверить можно
  только на твоей машине.

# Этап 2: голос (Piper TTS + полудуплекс)

Ответ LLM теперь ещё и озвучивается — локально, бесплатно, без обращения к
облаку (тот же принцип, что и с Whisper: голос остаётся на твоей машине).

## Настройка

1. Скачай голосовую модель Piper (нужны ДВА файла — `.onnx` и `.onnx.json`
   рядом). Список русских голосов: `dmitri`, `denis`, `irina`, `ruslan`.
   Пример (medium — хороший баланс качества/скорости):
   ```bash
   mkdir -p ~/.local/share/piper && cd ~/.local/share/piper
   wget https://huggingface.co/rhasspy/piper-voices/resolve/main/ru/ru_RU/dmitri/medium/ru_RU-dmitri-medium.onnx
   wget https://huggingface.co/rhasspy/piper-voices/resolve/main/ru/ru_RU/dmitri/medium/ru_RU-dmitri-medium.onnx.json
   ```
2. Установи переменную окружения перед запуском `server.py`:
   ```bash
   export PIPER_MODEL_PATH=~/.local/share/piper/ru_RU-dmitri-medium.onnx
   ```
3. Если `PIPER_MODEL_PATH` не задан (или файл не найден) — сервер **не
   падает**, печатает предупреждение и работает без озвучки, только текстом
   в UI, как на предыдущем этапе.

## Про будущее железо (отдельный микрофон + колонка)

Код НЕ выбирает конкретное устройство ввода/вывода — `AudioRecorder.cpp`
использует системный микрофон по умолчанию, `sounddevice.play()` в
`voice/tts.py` использует системную колонку по умолчанию. Это значит: если в
настройках звука ОС выставить default input = микрофон от наушников,
default output = колонка (JBL и т.п.) — маршрутизация "микрофон отдельно,
колонка отдельно" уже работает сама, без единой строчки кода про конкретные
устройства. Ничего доделывать для этого не нужно.

## Архитектура

- `framework/voice/tts.py` — `TextToSpeech.speak(text)`: синтезирует речь
  через Piper (Python API, не CLI) и воспроизводит её через `sounddevice`
  (та же PortAudio, что и в C++ ядре — общая нативная библиотека). Вызов
  блокирующий — это осознанно: вызывающий код должен точно знать момент,
  когда озвучка закончилась, чтобы снять MUTE с микрофона.
- `framework/voice/control.py` — `ControlChannel`: канал Python → C++ ядро
  (порт 5557, тот же принцип "Python — хаб", что и остальные каналы).
  Отправляет `"MUTE"`/`"UNMUTE"` вокруг вызова `tts.speak()`.
- `core/include/ControlListener.h` — принимает MUTE/UNMUTE в отдельном
  потоке. Сокет читается с таймаутом (`RCVTIMEO`), поэтому поток сам
  просыпается и проверяет флаг остановки — не нужно закрывать ZMQ-сокет из
  чужого потока (это было бы небезопасно, libzmq не потокобезопасен на
  уровне одного сокета).
- `core/src/main.cpp`: пока `MUTE` активен — кадр с микрофона всё равно
  вычитывается (чтобы не переполнить буфер PortAudio), но полностью
  игнорируется: не идёт ни в VAD, ни в буфер фразы. Если фраза была "в
  процессе записи" в момент прихода MUTE — она обрывается и не отправляется
  (в неё уже могла попасть перекличка TTS). При выходе из MUTE скрытое
  состояние Silero VAD сбрасывается (`vad.Reset()`), чтобы не тащить через
  паузу RNN-состояние.

**Это грубый полудуплекс, не полноценное эхоподавление (AEC).** Пока Джарвис
говорит — тебя он временно не услышит, даже если ты его перебиваешь. Полный
"живой" barge-in (можно перебить ответ на середине) — отдельная, более
сложная задача на будущее (см. план в переписке с разработчиком).

## Что проверено (без реального синтеза — модель Piper весит десятки
мегабайт и качается с huggingface.co, недоступного в этой песочнице,
поэтому это mock-тесты речевого движка и реальный тест управляющей логики):

- Установленный `piper-tts` (1.6.0) и его Python API (`PiperVoice.load`,
  `voice.synthesize()`, формат `AudioChunk.audio_int16_bytes`,
  `voice.config.sample_rate`) подтверждены интроспекцией установленного
  пакета, не по памяти.
- `TextToSpeech` — мок-тест: чанки синтеза корректно склеиваются в один
  массив и уходят в `sd.play()` с правильным sample rate и `blocking=True`.
- Обработка отсутствующей/несуществующей модели — понятная ошибка, сервер
  не падает.
- **Логика переходов MUTE/UNMUTE в C++** — реальный скомпилированный
  `ControlListener` реально принял `MUTE`, отправленный по ZMQ (полный
  бинарник запустить в песочнице целиком нельзя - нет физического
  микрофона, `AudioRecorder.Start()` падает на "нет доступных устройств", но
  сам приёмник команд подтверждён). Отдельно юнит-тестом на симуляции
  состояний проверены все переходы: обрыв фразы "в процессе" при входе в
  MUTE, полный игнор кадров во время MUTE, ровно один вызов `vad.Reset()`
  при выходе из MUTE (не ноль, не два).
- Полный e2e через `server.py` (с моком LLM и моком Piper): подтверждён
  порядок `MUTE → синтез → UNMUTE → ответ в UI`, и отдельно — что `UNMUTE`
  **гарантированно уходит даже если синтез речи упал с исключением**
  (иначе микрофон завис бы замьюченным навсегда до перезапуска ядра).
- **Не проверено**: реальный синтез настоящего голоса и реальное
  воспроизведение через колонку — для этого нужна скачанная модель и
  физическое аудио-устройство, недоступные в песочнице. Проверяется на
  твоей машине.

# Раунд 6: фикс по реальным логам с живого теста

## Баг: диалоговое окно фактически не работало

Окно активного диалога (10 сек) отсчитывалось от момента, **когда была
произнесена фраза с "Джарвис"**, а не от момента, когда Джарвис **закончил
отвечать**. Между этими моментами проходит распознавание + запрос к LLM +
озвучка через Piper — вместе легко несколько секунд. К моменту, когда ответ
дозвучал, окно уже могло истечь, и у пользователя физически не оставалось
времени ответить без повтора имени.

Это же объясняло вторую жалобу — "LLM не помнит последние сообщения": раз
окно почти всегда было уже мертво к следующей фразе с "Джарвис", каждая
такая фраза распознавалась как НОВАЯ сессия и стирала историю разговора
(`dialog_manager.reset()`).

**Исправлено** в `server.py`: окно теперь активируется (`dialog.activate(...)`)
ПОСЛЕ ответа, текущим временем (`time.time()`), а не временем исходного
вопроса (`capture_ts`). Пользователю нужны 10 секунд ПОСЛЕ того, как он
услышал ответ, а не 10 секунд с момента вопроса.

Проверено двумя сценариями:
- Обработка искусственно замедлена дольше, чем длина окна (3.1с обработки
  против 2с окна) — фраза без повтора имени всё равно корректно распознана
  как продолжение диалога (`Команда в диалоге`), история сохранена.
- Реально долгая пауза (3с при окне в 1с) — сессия корректно завершается,
  `dialog_manager.reset()` вызывается заново, старый контекст не тащится.

## Whisper `base` → `small`, настраиваемо через переменную окружения

По логам видно регулярные ошибки распознавания ("темножить" вместо
"умножить", "Оно скажешь" вместо "ну скажи" и т.п.) — ожидаемо для самой
маленькой модели. Добавлены переменные окружения:
```bash
export WHISPER_MODEL_SIZE=small   # по умолчанию теперь small (было base)
export WHISPER_DEVICE=cpu
export WHISPER_COMPUTE_TYPE=int8
```
Если ошибок распознавания всё ещё много — можно поднять до `medium` (точнее,
но заметно медленнее на голом CPU без GPU).

# Раунд 7: новые инструменты (управление компьютером)

Добавлены в `framework/agents/tools.py` — по инструкции из докстринга того
же файла (написать функцию → добавить схему в `TOOL_SCHEMAS` → добавить в
`TOOL_IMPLEMENTATIONS`), всё в одном месте, `dialog_manager.py` не тронут.

- **`open_website(url_or_query)`** — открывает сайт или гуглит запрос, через
  стандартный `webbrowser` (одинаково работает на Linux/Windows/macOS без
  веток по ОС).
- **`open_application(app_name)`** — открывает приложение **строго по
  белому списку** (`ALLOWED_APPLICATIONS_LINUX`/`_WINDOWS` в начале файла).
  Это намеренно: команда приходит от LLM, реагирующей на текст пользователя
  (в т.ч. искажённый распознаванием) - без белого списка это была бы прямая
  дыра для выполнения произвольных команд через промпт-инъекцию. Название
  ищется нечётким совпадением (`rapidfuzz`), чтобы прощать неточности STT.
  Списки под Linux Mint дефолтные (`xed`, `nemo` и т.п.) — поправь под свои
  реально установленные программы, если что-то не запускается.
- **`set_volume(level)` / `adjust_volume(direction, step)`** — громкость
  через `pactl` (PulseAudio/PipeWire, стоит по умолчанию на Mint/Ubuntu).
  Значения всегда клампятся в разумный диапазон на стороне кода, а не
  доверяются модели как есть.
- **`media_control(action)`** — пауза/трек вперёд/назад через `playerctl`
  (работает с любым MPRIS-плеером: Spotify, VLC, браузеры). Если команда не
  установлена — `sudo apt install playerctl`.
- **`set_timer(seconds, message)`** — единственный инструмент, который не
  укладывается в "функция сразу вернула результат": результат должен
  прозвучать ПОЗЖЕ. Реализовано через `threading.Timer` + функцию
  "уведомитель" (`register_timer_notifier`), которую `server.py`
  регистрирует один раз при старте. `tools.py` сам ничего не знает
  про TTS/ZMQ — уведомитель просто зовёт общую функцию `speak_and_notify()`
  в `server.py`, которая теперь используется и для обычных ответов LLM, и
  для сработавших таймеров - через общий `tts_lock`, чтобы обычный ответ и
  сработавший в то же время таймер не наложились друг на друга по звуку.

## Про перенос на Windows позже

Все системные инструменты (`open_application`, громкость, медиа) уже
проверяют `platform.system()` и на Windows возвращают понятную ошибку
"пока не реализовано" вместо попытки выполнить linux-команду. Когда дойдёшь
до переноса - дописывать нужно будет только реализацию внутри уже
существующих функций (`if _IS_WINDOWS: ...`), схемы и вся остальная
архитектура не меняются.

## Что проверено

- Инъекция через `app_name` (`"калькулятор; rm -rf /"`) — нечёткое
  совпадение корректно находит ближайшее ИЗВЕСТНОЕ имя ("калькулятор") и
  запускает ТОЛЬКО фиксированную команду из белого списка; вредоносная часть
  строки никогда не попадает в `subprocess`.
- Клампинг громкости (150→100%, -30→0%, шаг 200→50%) — юнит-тест с
  замоканным `pactl`.
- `set_timer` — таймер возвращает ответ немедленно (не блокирует), реально
  срабатывает по времени (проверено с точностью до сотых секунды).
- Полный e2e через `server.py`: команда "поставь таймер на 2 секунды" →
  LLM вызывает `set_timer` → мгновенное подтверждение в UI+TTS → через 2
  секунды таймер срабатывает из своего потока → корректно уходит в UI и
  озвучивается через тот же `tts_lock`, что и обычные ответы.
- **Не проверено**: реальные вызовы `xdg-open`/`pactl`/`playerctl` на живой
  системе — в песочнице нет ни браузера, ни звуковой системы, ни этих
  бинарников. Проверяется на твоей машине.

# Раунд 10: стриминг ответа + настоящее прерывание (barge-in)

Самое важное изменение с точки зрения "ощущается как живой разговор", а не
просто "работает технически". Два независимых, но связанных улучшения.

## A) Стриминг ответа LLM по предложениям

**Проблема была:** `DialogManager.handle()` ждал ПОЛНЫЙ ответ модели целиком,
только потом Piper начинал говорить. На ответе из 2-3 предложений набегало
несколько секунд тишины после того как пользователь договорил, прежде чем
Джарвис открывал рот - это и есть главный разрыв с "как в живом разговоре".

**Исправлено:** `DialogManager.handle_streaming(text, on_sentence_ready,
should_abort)` в `agents/dialog_manager.py` читает ответ через `stream=True`
(Server-Sent Events) и зовёт `on_sentence_ready(sentence)` на каждое
законченное предложение сразу, как оно готово - `voice/streaming_speaker.py`
(`StreamingSpeaker`) сразу же начинает его озвучивать, пока LLM ещё
генерирует продолжение.

Так как здесь нет "автоматического" стриминга функций (в отличие от
нестримингового вызова), function calling пришлось собирать вручную:
аргументы инструмента прилетают ФРАГМЕНТАМИ по разным чанкам потока
(`delta.tool_calls[i].function.arguments` - частичные строки JSON),
собираются по `index` и парсятся только когда весь фрагмент собран.

Разбивка на предложения - простой regex по знакам конца предложения
(`.!?...`) с пробелом/концом строки после. Не идеально (не отличит "3.14" от
"3. Дальше" в редком краевом случае), но простое и надёжное решение без
внешних NLP-библиотек.

## Б) Настоящее прерывание (barge-in)

**Было:** пока Джарвис говорит, C++ ядро полностью игнорировало микрофон
(`if (muted_now) continue;`) - пользователь физически не мог его перебить,
только дождаться конца ответа.

**Стало:** микрофон больше не отключается. Вместо этого, пока идёт ответ
(`is_muted`/MUTE от Python), VAD в `main.cpp` использует БОЛЕЕ СТРОГИЙ порог
(`VAD_SPEECH_THRESHOLD_INTERRUPT = 0.85` вместо обычных `0.55`, и
`CONFIRM_FRAMES_INTERRUPT = 5` кадров подряд вместо обычных `2`, то есть
~160мс уверенной речи, а не короткий всплеск). Логика: собственный голос
Джарвиса, просочившийся из динамика в микрофон, обычно тише и "смазаннее"
настоящей речи прямо в микрофон - завышенный порог отсеивает самоперекличку,
но уверенный голос пользователя всё равно её пробивает.

Когда фраза всё-таки проходит эти строгие условия во время ответа, она
уходит по ТОМУ ЖЕ каналу, что и обычные фразы (никакого нового протокола не
понадобилось) - а `server.py` в receive-цикле теперь зовёт
`speaker.abort()` на КАЖДУЮ входящую фразу перед тем как поставить её в
очередь. `abort()` безопасен всегда (если Джарвис молчит - это no-op), а
если говорил - `TextToSpeech.stop()` (через `sd.stop()`) останавливает
воспроизведение НЕМЕДЛЕННО (подтверждено по исходникам `sounddevice`:
`stream.stop()` вызывает тот же `finished_callback`, что снимает блокировку
`sd.play(blocking=True)` - остановка из чужого потока работает без задержки).

Также `should_abort()` передаётся в `handle_streaming()` - если ответ
прерван, чтение потока от LLM останавливается раньше времени, не дочитывая
(и не доплачивая за) остаток ответа, который всё равно не озвучится.

**Важная деталь, которую пришлось поправить заодно:** окно "активного
диалога" раньше активировалось только ПОСЛЕ ответа - значит, перебивание
без повтора "Джарвис" посреди ЕЩЁ НЕ закончившегося ответа не признавалось
бы продолжением разговора. Теперь `dialog.activate()` вызывается и в начале
обработки, и после - окно открыто на всё время ответа, а не только после.

**Честная оговорка:** это НЕ полноценное эхоподавление (AEC) - компромисс,
работающий за счёт разницы порогов, а не за счёт вычитания эха из сигнала.
Если микрофон физически рядом с колонкой и говорить тихо - может не
сработать идеально. Планируемое физическое разнесение микрофона и колонки
(наушники + JBL-колонка) должно этому только помочь.

## Что проверено

- Стриминг: мок-тест с задержкой между чанками показал, что первое
  предложение озвучивается через 0.05с, хотя весь ответ занимает ~0.3с -
  предложения приходят по мере готовности, не все разом в конце.
- Фрагментированные аргументы инструмента (частями по разным чанкам)
  корректно собираются, инструмент реально выполняется (`calculate`
  посчитал 7*8=56).
- `should_abort()` корректно останавливает чтение потока раньше времени
  (4 чанка из 9 в тесте) - не дочитывает лишнее.
- Обработка сетевых сбоев и до, и ПОСЕРЕДИНЕ стрима - частичный текст,
  который уже пришёл, не теряется, а озвучивается как есть.
- Адаптивные пороги VAD (C++) - юнит-тест на 4 сценариях: обычная громкость
  не прерывает во время речи Джарвиса, но прерывает в обычном режиме;
  уверенная громкость, выдержанная нужное число кадров, прерывает; короткий
  всплеск (меньше кадров, чем нужно) - не успевает прервать.
- Полный e2e через `server.py` (с реалистичной симуляцией воспроизведения,
  которое "звучит" заданное время и прерывается `stop()`): ответ на первую
  фразу начал звучать, затем пришла фраза-перебивание - второе предложение
  первого ответа **гарантированно не было синтезировано** (проверено по
  логу самого фейкового Piper, не только по факту вызова stop()), и сразу
  пошёл ответ на фразу-перебивание.
- **Не проверено**: реальное качество работы порога `0.85` на живом
  железе/акустике - подбирался по смыслу (существенно строже обычного), но
  не откалиброван на реальной записи твоей комнаты/микрофона. Если будет
  либо слишком легко перебивать себя эхом, либо наоборот сложно перебить
  голосом - подкрути VAD_SPEECH_THRESHOLD_INTERRUPT/CONFIRM_FRAMES_INTERRUPT
  в `core/src/main.cpp`.

# Раунд 11: отмена in-flight LLM/tool-call при перебивании + мгновенный filler

**Проблема (из внешнего аудита):** barge-in (раунд 10) останавливал TTS
немедленно, но если пользователь перебивал ровно в момент, когда LLM
выполняла tool-call (или между хопами цикла function-calling), обработка
предыдущей, уже неактуальной фразы всё равно докручивалась до конца -
следующая фраза ждала в очереди. Заодно нашёлся смежный протокольный баг:
при отмене assistant-сообщение с НЕВЫПОЛНЕННЫМИ tool_calls всё равно
попадало в постоянную историю - следующий же запрос к LLM с такой историей
падал бы ошибкой (dangling tool_call).

**Что сделано** (`agents/dialog_manager.py`):
- `should_abort()` теперь проверяется в ТРЁХ точках: в начале каждого хопа
  (до сетевого запроса), после каждого чанка стрима (как раньше), и перед
  выполнением КАЖДОГО отдельного tool-call (не только "после всех").
- При отмене на любом этапе история откатывается ПОЛНОСТЬЮ до состояния "до
  этой реплики" (через снимок длины, а не хрупкий `.pop()` одного элемента) -
  никаких "подвешенных" tool_calls без ответа больше не остаётся.
- Проверено `test_abort_scenarios.py` (мок-клиент, без сети): отмена до
  первого хопа, отмена с недовыполненным tool_call, отмена перед вторым из
  двух инструментов (первый уже выполнился - его сайд-эффект НЕ откатывается,
  но история всё равно чистая) + регрессия обычного tool-calling без отмены.

**Мгновенный filler** (`voice/streaming_speaker.py`, `voice/tts.py`):
короткие фразы ("Секунду.", "Так.", "Сейчас.") синтезируются ОДИН РАЗ при
старте сервера (см. `FILLER_PHRASES`/`FILLER_DELAY_SECONDS` в `server.py`) и
воспроизводятся мгновенно, если реальный ответ LLM не успел прийти за
`FILLER_DELAY_SECONDS` (по умолчанию 0.35с) - вместо полной тишины во время
ожидания. Если ответ уже готов раньше - filler не звучит вообще, никакой
лишней задержки для быстрых ответов. Проверено `test_filler.py` (фейковый
TTS с логом вызовов, без реального звука): медленный ответ - filler звучит
первым; быстрый ответ - filler пропущен; abort() до срабатывания таймера -
filler не звучит вообще.

# Раунд 12: intent-router - бытовые команды в обход LLM

**Проблема:** даже идеальная LLM даёт 1-3+ секунды до первого звука ответа
(сеть + инференс). Для "тише", "пауза", "таймер 5 минут", "открой браузер"
это ощущается как заметный лаг там, где не должно быть вообще никакой
задержки.

**Что сделано** (`agents/intent_router.py`, новый модуль): распознаёт и
СРАЗУ выполняет (в обход `dialog_manager`/LLM целиком) громкость
(`set_volume`/`adjust_volume`), медиа (play/pause/next/previous через
`playerctl`), таймер (по цифрам: "5 минут", "30 секунд", "полчаса") и
"открой X" (fuzzy-поиск по тому же whitelist, что и обычный tool, но с более
строгим порогом уверенности). Встроен в `server.py` ПЕРЕД вызовом
`dialog_manager.handle_streaming()` в обеих ветках (wake-word и продолжение
диалога).

Принцип "уверен или не лезу": при малейшей неуверенности (длинная/составная
фраза - ограничение `MAX_WORDS_FOR_INSTANT_COMMAND`, нет чёткого совпадения,
непонятный аргумент) возвращает `None`, и фраза уходит по ОБЫЧНОМУ пути
через LLM, как будто router'а не было вовсе. Ложное срабатывание (выполнить
не то действие) считается хуже, чем лишняя секунда ожидания LLM.

Работает ДАЖЕ без `LLM_API_KEY` (`dialog_manager is None`) - громкость,
медиа, таймер и открытие приложений теперь не требуют LLM вообще.

Проверено `test_intent_router.py` (фейковые инструменты с логом вызовов,
12 сценариев) - включая негативные: длинная фраза с "тише" внутри не
триггерит громкость, "дальше" без слова "трек"/"музыка" рядом не путается
с несвязанным контекстом, неуверенное распознавание приложения проваливается
в LLM, а не открывает наугад.

# Раунд 13: UI 2.0 - состояния, роли, кнопка прервать

**Проблема:** UI был логом, а не собеседником - статус-лейбл + один
`QTextEdit`, голые строки без ролей, без индикации "что сейчас происходит",
без возможности прервать иначе как голосом.

**Что сделано:**
- Протокол `server.py` → UI (порт 5556) стал структурированным JSON вместо
  голых строк - см. `send_ui_event()`: `{"type": "state", "value": "idle" |
  "thinking" | "speaking"}`, `{"type": "user_message", "text": ..., "heard":
  bool}`, `{"type": "assistant_message", "text": ...}`.
- Состояние "думаю" выставляется МАКСИМАЛЬНО рано - сразу как фраза взята в
  обработку, до распознавания. "Говорю" - на время всего "ответного" окна
  (MUTE активен). Возврат в "слушаю" ГАРАНТИРОВАН через `finally` в
  `transcribe_worker` - даже при исключении индикатор не зависнет.
- Распознанный текст пользователя показывается в UI СРАЗУ, а не склеенным с
  ответом в конце - в том числе фоновая речь вне активного окна (`heard:
  false`), отображается бледным, чтобы не путать с настоящей командой.
- Новый канал UI → `server.py` (порт 5558, `ui_command_listener`) - кнопка
  "⏹ Прервать" в UI дёргает ровно тот же `speaker.abort()`, что и голосовой
  barge-in. Отдельный сокет, а не тот же самый 5556 туда-обратно - zmq-сокет
  не гарантированно потокобезопасен при использовании из разных потоков
  одновременно, а 5556 уже занят потоком `transcribe_worker` на отправку.
- `main.py` переписан целиком под новый протокол - старая версия UI (голые
  строки) с этим сервером работать не будет.

Проверено: headless-прогон UI (`QT_QPA_PLATFORM=offscreen`) - переключение
состояний, включение/выключение кнопки прервать, HTML-рендер истории;
интеграционный тест `ui_command_listener` (реальные zmq-сокеты, без Qt) -
команда "прервать" доходит и вызывает `speaker.abort()` ровно один раз,
мусорные/нерелевантные сообщения не роняют поток и не дёргают abort зря.

# Раунд 14: wake-word (B2) - механика готова и проверена, модели под русский пока нет

**Вопрос, с которого всё началось:** зачем вообще отдельный wake-word, если
уже есть Silero VAD? Это РАЗНЫЕ задачи: VAD режет непрерывный звук на фразы
("человек начал/закончил говорить"), wake-word проверяет "было ли сказано
именно слово-активатор". Сейчас это делает Whisper - то есть **на каждую**
фразу (даже фоновую болтовню, ТВ и т.п.) гоняется тяжёлая ASR-модель целиком,
просто чтобы потом fuzzy-поиском проверить наличие "джарвис" в тексте.
Отдельный wake-word - это крошечная модель, которая крутится ПОСТОЯННО, на
сырых кадрах, и делает только одно: да/нет. VAD никуда не девается - как
резал команду ПОСЛЕ активации, так и режет.

## Что сделано и ПРОВЕРЕНО по-настоящему (не просто "скомпилировалось")

Новый `core/WakeWordDetector.{h,cpp}` - C++-реализация конвейера
openWakeWord (`melspectrogram.onnx` -> `embedding_model.onnx` -> модель
конкретного слова), по образцу `SileroVAD`. Вся арифметика (нормализация
`x/10+2` выхода mel-модели, приведение int16->float БЕЗ деления на 32768,
скользящее окно эмбеддинга шагом 8 mel-кадров, буфер на последние 16
эмбеддингов) сверена с официальным исходником `openwakeword/utils.py` и
**реально прогнана** против настоящих ONNX-моделей (скачаны с официальных
релизов openWakeWord) и синтезированной речи (espeak-ng + ffmpeg-ресемплинг
до 16kHz):

- Python-прототип конвейера и C++-реализация дают **совпадающий результат**
  (0.38707 в обеих версиях) на фразе "hey jarvis, what is the weather like
  today" - это кросс-проверка C++ против независимого эталона, а не просто
  "не упало".
- На контрольной фразе без слова-активатора скор держится в районе 0.0001 -
  ложных срабатываний на непричастную речь нет.
- Полная сборка ядра (`cmake && make`) проходит чисто с новым файлом в
  `CMakeLists.txt`.
- Детектор **полностью опционален и по умолчанию выключен** - если не
  заданы все три переменные окружения (`WAKEWORD_MELSPEC_MODEL`,
  `WAKEWORD_EMBEDDING_MODEL`, `WAKEWORD_MODEL`) или файлы моделей не
  найдены, конструктор ловит это сам, печатает предупреждение и ядро
  работает РОВНО как раньше (Whisper + fuzzy-поиск). Проверено обоими
  путями: без переменных (детектор молчит) и с ними (детектор включается) -
  оба раза до самого ALSA (реального аудиоустройства) доходит без единой
  ошибки.
- Готовый тестовый набор для sanity-check конвейера БЕЗ настоящей русской
  модели - `core/wakeword_test_fixtures/` (см. README там же) -
  англоязычная community-модель "hey jarvis" + тестовые WAV, чтобы можно
  было проверить именно код, а не гадать, обучена ли модель.

Интеграция в `main.cpp`: детектор кормится тем же сырым (не усиленным
автогейном) 512-сэмпловым кадром, что и Whisper в итоге получает. При
срабатывании (гистерезис - 3 кадра подряд выше порога 0.5, не единичный
всплеск, плюс ~2с "остывания" после срабатывания, чтобы не сработать
повторно на хвосте того же произнесения) фраза начинает записываться
НЕМЕДЛЕННО, в обход обычного антидребезга VAD (`CONFIRM_FRAMES`) - именно
эта задержка и есть то, ради чего весь B2 затевался.

## Чего НЕТ (и почему это не "ещё один файл", а отдельная задача)

**Готовой модели под русское произношение "Джарвис" не существует.**
openWakeWord официально поддерживает только английский (синтетические
голоса для обучения - все на английском). Единственная готовая модель
семейства "jarvis" - `hey_jarvis` - обучена на АНГЛИЙСКОЕ произношение и
фонетически не имеет отношения к "Джарвис".

Два реальных пути получить рабочую модель:

1. **Хостинговый тренер** - https://openwakeword.com/train. Судя по
   описанию, поддерживает 20+ языков и генерацию через TTS + впрыск
   собственного голоса, экспортирует ONNX. Не проверял сам (нет доступа
   из песочницы) - стоит попробовать первым, это может занять минуты, а не
   часы.
2. **Локальное обучение** через собственный `automatic_model_training`
   ноутбук openWakeWord - только МАЛЕНЬКИЙ классификатор (последний блок
   конвейера) обучается заново, `melspectrogram`/`embedding` остаются
   замороженными (уже есть, скачаны). Позитивные примеры можно
   сгенерировать локально через УЖЕ ЕСТЬ в проекте Piper TTS (см.
   `voice/tts.py`) - несколько вариаций скорости/интонации на слове
   "Джарвис". Негативные примеры (фоновая речь/шум) нужно набрать отдельно
   - это самая трудоёмкая часть, требует некоторого количества GPU-часов на
   обучение самого классификатора (сам классификатор маленький, не полная
   ASR-модель).

Это осознанно оставлено вам - требует скачивания больших датасетов и/или
GPU, что невозможно сделать в этой песочнице. Как только появится
`.onnx`-файл (из любого источника) - он подключается ОДНОЙ строкой в
переменных окружения, без изменений в коде (`melspectrogram`/`embedding`
модели переиспользуются как есть, они не зависят от конкретного слова).

**Временная заглушка на время разработки:** можно уже сейчас гонять
англоязычную `hey_jarvis` (см. `core/wakeword_test_fixtures/`) и говорить
именно "hey jarvis" вслух, пока не появится русская модель - переключение на
неё потом не потребует ни строчки кода, только замену `WAKEWORD_MODEL` на
новый файл. Полезно знать: на измеренных данных даже у ПРАВИЛЬНО
произнесённой "hey jarvis" скор держится в районе 0.35-0.4 (см. выше) - порог
по умолчанию 0.5 для неё многовато. Три параметра гистерезиса настраиваются
через переменные окружения без пересборки:

```bash
export WAKEWORD_THRESHOLD=0.3          # по умолчанию 0.5
export WAKEWORD_TRIGGER_LEVEL=3        # кадров подряд выше порога
export WAKEWORD_REFRACTORY_FRAMES=60   # кадров "остывания" после срабатывания (~2с)
```

# Раунд 15: C1 - расширение белого списка приложений/дисков

**`agents/tools/apps.py` - починен реальный баг, не только "добавлены
приложения".** На Windows код брал `candidates[0]` вслепую, вообще не
проверяя, установлено ли приложение на самом деле - "не удалось запустить"
можно было получить даже для установленного приложения, если порядок
кандидатов не совпал с реальностью. Теперь `find_installed_candidate`
(`_shared.py`) реально проверяет наличие и умеет glob-паттерны с `*`/`%`
(нужно для версионированных папок установки типа `Steam\steamapps\...` или
`AppData\Local\<App>\app-1.2.3\`) - при нескольких совпадениях берёт САМУЮ
СВЕЖУЮ по времени изменения (`mtime`), а не первую попавшуюся. Это открыло
дорогу добавить на Windows Steam/Discord/Spotify/Roblox/Roblox Studio -
все ставятся в версионированные подпапки, раньше их нельзя было надёжно
найти простым `shutil.which`.

**`agents/tools/folders.py` - `_discover_volumes()`.** Диски/флешки
детектятся ДИНАМИЧЕСКИ при КАЖДОМ вызове `open_folder()`, а не берутся из
статического списка, собранного при старте сервера - флешку могли воткнуть
(или вынуть) в любой момент между репликами, закэшированный на старте
список неизбежно устарел бы.

**Незакрытое, и не может быть закрыто без юзера:** в `ALLOWED_FOLDERS`
(`folders.py`) закомментированы placeholder-строки под папки проектов
("Джарвис", route control server) - точные пути на реальной машине юзера
знать неоткуда (эта песочница - не его компьютер), вписать их может
только он сам.

# Раунд 16: C2 - контекст среды (активное окно/буфер обмена/что играет)

Новый `agents/tools/environment.py` - три read-only инструмента, не
требующие подтверждения (в отличие от C3, раунд 17 - ниже): `get_active_window`

# Раунд 17: C3 - голосовое подтверждение опасных действий

**Проблема:** "открой браузер" -> сразу открывает, без вопросов - ок для
безобидных действий, но для по-настоящему необратимых/опасных
(заблокировать компьютер, в будущем - выключить/удалить что-то) хочется явное
"да" перед выполнением, а не слепое доверие тому, что STT+LLM правильно
поняли команду с первого раза.

**Дизайн - подтверждение НЕ доверяется LLM, оно детерминированное:**
Новый `agents/confirmation.py` - реестр `DANGEROUS_TOOLS` (сейчас там
`lock_computer` - единственное по-настоящему опасное действие в проекте на
сегодня; добавить новое - одна строка в словаре, без другого кода) плюс
`match_confirmation_reply()` - разбор да/нет ПРОСТЫМ списком слов, без
обращения к LLM (тот же принцип "уверен или не лезу", что и в
`intent_router.py`).

Когда модель просит вызвать опасный инструмент - `dialog_manager.py` его
**не выполняет**. Вместо этого задаёт жёстко заданный вопрос ("Точно
заблокировать компьютер? Скажи «да» или «нет».") и останавливает цикл хопов
СРАЗУ - не даёт модели самой придумать, как спросить (и тем более не даёт ей
шанса просто доложить "готово", не выполнив ничего на самом деле - в архив
контекста ушёл бы обманчивый ответ). Если в одном ответе несколько
tool-вызовов и опасный не первый - предыдущие безопасные успевают
выполниться, а с опасного момента всё останавливается (заблокировать что-то
ПОСЛЕ несогласованного действия - хуже, чем ничего не сделать).

Следующая фраза пользователя разбирается СЕРВЕРОМ, не LLM: однозначное
да/нет (короткая фраза) выполняет/отменяет действие МГНОВЕННО, без единого
сетевого запроса. Неоднозначный ответ (либо оба слова сразу, либо ни одного,
либо длинная фраза) - НЕ считается ни согласием, ни отказом: ожидание тихо
сбрасывается, и фраза уходит по обычному пути, как будто вопроса подтверждения
не было. Тайм-аут 12 секунд - если пользователь просто не ответил, действие
тихо отменяется.

Отдельно нашли и починили реальный баг при разработке: если "не" считать
отдельным словом-отрицанием, "не знаю" распознавалось бы как "нет" (отказ) -
хотя семантически это не отказ, а неуверенность. Убрали одиночное "не" из
списка, составные отрицания ("не надо", "не нужно") ловятся отдельной
проверкой по ЦЕЛОЙ фразе.

Проверено: `test_confirmation_matcher.py` (да/нет/неоднозначно на россыпи
формулировок, включая тот самый "не знаю"), `test_dangerous_tool_interception.py`
(dialog_manager реально НЕ вызывает `lock_computer`, история без "подвешенного"
tool_call, батч из безопасного+опасного вызова останавливается ровно на
опасном) - оба через мок-клиент, без сети.

# Раунд 19: A1-A2 - единый запуск и автоперезапуск

До этого раунда три процесса (core/server.py/main.py) запускались вручную
в трёх терминалах строго в определённом порядке - см. раздел "Как собрать
и запустить" ниже. Работало, но при падении любого из трёх процессов (а
core может упасть от банальной ошибки ALSA, server.py - от сетевого сбоя
Whisper) остальные два оставались висеть в рассинхроне без единого
уведомления.

**`scripts/start.sh`** - новый единый скрипт запуска. Что делает:

- поднимает все три процесса в правильном порядке (server -> пауза
  `JARVIS_STARTUP_DELAY` на bind портов -> core -> UI);
- watchdog-цикл (`kill -0` раз в `JARVIS_POLL_INTERVAL` секунд): если
  падает ЛЮБОЙ из трёх - перезапускаются ВСЕ ТРИ, а не только упавший.
  **Сознательное решение, не недосмотр:** core и server держат состояние
  друг о друге через конкретные zmq-сокеты (5555/5557) - точечный
  перезапуск одного с "чистого листа" рискует рассинхронить остальные два
  тише, чем просто их не перезапустить вовсе. Дороже по времени (доли
  секунды на весь узел), зато детерминированно - тот же принцип, что и
  "уверен или не лезу" из раунда 12, применённый к инфраструктуре;
- защита от restart-шторма: если перезапусков больше, чем
  `JARVIS_MAX_RESTARTS` за `JARVIS_RESTART_WINDOW` секунд (по умолчанию
  5 за 60с) - скрипт сдаётся с кодом 1 вместо бесконечного цикла
  перезапуска (типичный триггер - ядро вообще не собрано);
- команды каждого процесса - в `CORE_CMD`/`SERVER_CMD`/`UI_CMD` (по
  умолчанию реальные пути проекта), подменяемые через env - именно так их
  подменяют тесты фейковыми процессами, без реального железа/зависимостей;
- preflight-проверка: если `core/build/jarvis_core` не собран - понятная
  ошибка сразу, а не пустой цикл рестартов;
- чистая остановка по `Ctrl+C`/`SIGTERM` (`scripts/stop.sh` - то же самое
  из другого терминала) - таймаут SIGTERM -> SIGKILL на каждый дочерний
  процесс, без "осиротевших" процессов после выхода.

**`deploy/systemd/jarvis.service`** - user-unit (не системный сервис - UI
на Qt нужна графическая сессия), оборачивающий тот же `start.sh` как
`ExecStart` с `Restart=on-failure`. Это ВТОРОЙ, независимый уровень
защиты: собственный watchdog в `start.sh` перезапускает три ДОЧЕРНИХ
процесса, а systemd - на случай, если упадёт сам скрипт целиком (например,
OOM-killer). Установка - см. комментарий в начале файла юнита; путь к
проекту невозможно знать заранее (как и с `folders.py` в раунде 15) -
юзер вписывает его сам при установке.

Проверено `test_launch_watchdog.py` - весь watchdog-цикл целиком через
подмену `CORE_CMD`/`SERVER_CMD`/`UI_CMD` на фейковые python-процессы
(`scripts/testdata/fake_worker.py` пишет свой pid при старте/остановке в
общий журнал событий, `fake_crash.py` падает сразу же): падение ОДНОГО из
трёх реально перезапускает все три (новые pid у всех, не только у
упавшего), `SIGTERM` останавливает всё чисто без сирот, restart-шторм
(процесс падает на каждом старте) останавливает скрипт с кодом 1, не
уходя в бесконечный цикл.

**Не входит в этот раунд (осознанно):** ротация логов в файл (A3 - логи
пока пишутся как есть, без ограничения размера) и `config.yaml`/

# Раунд 20: A3 - ротация логов

Продолжение раунда 19. После A1-A2 Джарвис может крутиться неделями под
systemd - а `logs/{server,core,ui,watchdog}.log` до этого только росли
через `>>` без всякого предела. Дальше диск.

**Проблема с обычным logrotate**: core/server/UI - долгоживущие процессы,
которые не умеют переоткрывать файл лога по сигналу (SIGHUP), в отличие
от того же nginx. Classic rename-based logrotate тут тихо сломался бы:
переименовали файл - процесс продолжает писать в старый (уже
переименованный) inode через уже открытый файловый дескриптор, а по
исходному имени появляется пустой файл, который никто не пишет.

**Решение - copytruncate прямо в `start.sh`.** Раз в
`JARVIS_POLL_INTERVAL` секунд (тем же циклом, что проверяет "живы ли
процессы") `rotate_all_logs()` смотрит размер каждого файла в `logs/`;
если он >= `JARVIS_LOG_MAX_BYTES` (по умолчанию 5 МиБ) - файл копируется
в архив (`server.log` -> `server.log.1` -> `server.log.2` -> ... -> `.N`,
где `N` = `JARVIS_LOG_BACKUPS`, старейший архив за пределами лимита
удаляется), а САМ файл обнуляется НА МЕСТЕ (`: > "$file"`), не
переименовывается. Почему это безопасно: все дочерние процессы пишут в
свои логи через `>>` (append-режим), а у append каждая запись сама ищет
конец файла перед тем, как писать - после truncate "конец" тут же
оказывается в начале, и следующий же write процесса просто попадает в
уже пустой (по факту новый) файл. Никого не перезапускаем и не сигналим -
процесс вообще не замечает, что с его логом что-то произошло.

Ротация применяется одинаково ко всем четырём файлам, включая собственный
`watchdog.log` скрипта - никакого отдельного случая для него.

Проверено `test_log_rotation.py` (переиспользует хелперы из
`test_launch_watchdog.py`, тот же паттерн, что и `test_tool_call_audit_log.py`
с `test_abort_scenarios.py`): фейковый процесс намеренно "спамит" в stdout
(новый необязательный параметр `fake_worker.py`, только для этого теста),
чтобы реально нагнать файл до порога. Проверено: архив `.log.1`
действительно появляется и не пустой; после ротации файл продолжает расти
дальше (то есть процесс не потерял, куда писать); при быстрой ротации по
кругу архивов никогда не оказывается больше, чем `JARVIS_LOG_BACKUPS`;
и отдельно - что сама ротация НЕ триггерит перезапуск процесса (это
операция только над файлом, никак не связанная с watchdog-логикой A1-A2).

Полная регрессия после этого раунда - 41 тест, все зелёные.

# Раунд 21: A4 - config.yaml + .env вместо россыпи env-переменных

До этого раунда несекретные настройки (модель Whisper, LLM base_url/model,
путь к голосу Piper, filler-фразы, URL личного бэкенда) и секреты
(`LLM_API_KEY`, `JARVIS_BACKEND_API_KEY`) были в одной куче - обычные
`export`-ы в шелле, разбросанные по четырём разным `.py`-файлам со своими
дефолтами внутри кода. Единственным источником правды был README.

**`framework/jarvis_config.py`** - новый модуль-загрузчик. Порядок
приоритета, если одна настройка задана в нескольких местах (выше -
главнее): переменная окружения, реально экспортированная в shell -> `.env`
(в корне проекта) -> `config/config.yaml` -> дефолт в коде вызывающего
модуля. **Обратная совместимость - основное требование к этому раунду:**
у кого уже настроено через `export ... >> ~/.bashrc` - ничего менять не
нужно, старые export'ы по-прежнему главнее всего, что лежит в новых
файлах.

Два разных метода в модуле, не один - специально:
- `get(env_var, yaml_path, default)` - для обычных настроек, смотрит и

- `get_secret(env_var, default)` - для API-ключей, **НИКОГДА** не
  заглядывает в `config.yaml` (даже если кто-то по ошибке впишет секрет
  туда - `get_secret` его не найдёт) - только `.env`/env. `config.yaml`
  предполагается пригодным для git, `.env` - нет.

**`config/config.yaml`** - несекретные настройки одним файлом:
`whisper.*`, `llm.*` (кроме ключа), `piper.*`, `filler.*`, `backend.url`.
**`.env.example`** - шаблон для секретов (`LLM_API_KEY`,
`JARVIS_BACKEND_API_KEY`) - копируется в `.env`, который в git не идёт.

Обновлены под новый загрузчик 4 файла, которые раньше сами читали

FILLER_*). Логика внутри не менялась - только откуда берётся значение.

**Осознанно НЕ вошло в этот раунд** - и вряд ли войдёт в `config.yaml`
вообще, без более крупного рефакторинга: `WAKEWORD_*` (их читает C++ ядро

Проверено `test_jarvis_config.py` (11 тестов, все через временные

# Раунд 22: B3 - мгновенная обратная связь "слушаю вас"

Из чек-листа B3 - "partial/streaming STT в UI (текст по ходу распознавания)".
Важная оговорка сразу: **настоящего партиала (текст слово за словом, пока
человек ещё говорит одну фразу) в этом раунде НЕТ и не могло быть дёшево**.
Архитектурная причина: C++ ядро режет речь на ГОТОВЫЕ фразы через Silero VAD
и отправляет в Python только уже полностью законченную фразу целиком - у
сервера физически нет доступа к аудио, пока фраза ещё звучит. Настоящий
партиал потребовал бы стриминга растущих кусков аудио ДО конца фразы -
изменение самой гранулярности передачи в C++ ядре, зона, где юзер прямо
попросил не лезть без крайней необходимости, и заметно более рискованное
и дорогое изменение, чем то, что сделано в этом раунде.

**Что сделано вместо этого - дёшево и честно, без выдуманного текста:**
до этого раунда UI не получала ВООБЩЕ никакой обратной связи, пока
пользователь говорил, - индикатор "слушаю" был статичным до тех пор, пока
VAD не решит, что фраза закончена, и Whisper её не распознает (секунды).
Теперь ядро шлёт лёгкий СИГНАЛ (без аудио, один zmq-фрейм вместо обычных
двух) в момент, когда VAD только увидел начало речи - почти бесплатно:
VAD и так уже это вычисляет для нарезки фраз, здесь просто добавлена
отправка уже готового факта.

**`core/include/PhraseSender.h`** - протокол расширен: кроме обычных фраз
(`"type":"phrase"`, 2 фрейма: заголовок + аудио) появились сигналы
(`"type":"speech_started"` / `"speech_discarded"`, 1 фрейм, без аудио) -
`EnqueueSignal()` рядом с существующим `Enqueue()`, та же очередь и
worker-поток, никакого нового канала/сокета.

**`core/src/main.cpp`** - два новых вызова:
- `EnqueueSignal("speech_started", ...)` - прямо в `BeginPhrase()`, сразу,
  как только VAD зафиксировал начало речи (или сработал wake-word);
- `EnqueueSignal("speech_discarded", ...)` - в ветке, где фраза оказалась
  короче `MIN_PHRASE_SAMPLES` и отбрасывается целиком. **Без этого сигнала
  UI застряла бы в "слушаю вас" навсегда** после случайного щелчка/кашля -
  `speech_started` уже отправили, а полной фразы вслед за ним не будет.

**`framework/audio_protocol.py`** (новый) - `parse_audio_message()`,
разбор multipart-сообщения от ядра, вынесен из `server.py` в отдельный
модуль БЕЗ тяжёлых зависимостей (только `json`/`time`, стандартная
библиотека) - специально, чтобы протокол тестировался без zmq и без
faster-whisper, которые server.py тянет при импорте.

**`framework/ui_state.py`** (новый) - `STATE_LABELS` (добавлено состояние
`listening_active`: "🎙️ Слушаю вас...") и `is_interruptible()`, вынесены
из `main.py` по той же причине - без PySide6, чтобы тестировать логику
кнопки "прервать" без поднятия Qt-приложения. **Важный нюанс:**
`listening_active` осознанно НЕ входит в `INTERRUPTIBLE_STATES` - до этого
раунда кнопка включалась по правилу `state != "idle"`, и новое состояние
ошибочно включило бы её тоже (прерывать-то нечего, Джарвис ещё не начал
отвечать) - правило сужено до `state in ("thinking", "speaking")`.

**`server.py`** - главный цикл приёма теперь смотрит `kind` результата
`parse_audio_message()`: `"signal"` с `speech_started` -> UI получает
`{"type":"state","value":"listening_active"}`, с `speech_discarded` ->
откат в `"idle"`; `"phrase"` - работает ровно как раньше.

**Реально скомпилировано и прогнано, не только написано:** полный
`cmake`-билд ядра в песочнице недоступен (сетевые ограничения на часть
пакетов Ubuntu, `onnxruntime` пользователь держит у себя отдельно), но
заголовки/библиотеки `zmq`/`portaudio` удалось вытащить вручную из .deb, и
`PhraseSender.h` с обоими новыми вызовами `EnqueueSignal()` собран,
слинкован и прогнан живьём против настоящего Python zmq-приёмника - на
проводе действительно `speech_started`/`phrase`/`speech_discarded` в
правильном формате и порядке (сигнал ВСЕГДА приходит раньше связанной с
ним фразы, так как FIFO-очередь одна на оба вида сообщений).

Проверено `test_streaming_feedback.py` (15 тестов, только `audio_protocol`
и `ui_state`, никаких тяжёлых зависимостей): разбор фразы/обоих типов
сигналов/невалидных сообщений (битый JSON, неправильное число фреймов,

# Раунд 23: B6 - локальный fallback-LLM без интернета

Из чек-листа B6 - "локальный fallback LLM (Phi/Qwen/llama.cpp) без
интернета". У юзера уже есть LM Studio с локальной Gemma-12B - но только
на Windows-машине (дуалбут/отдельный компьютер, не там, где крутится сам
Джарвис). Поэтому вместо того, чтобы тащить в проект ещё один рантайм
(llama.cpp/встроенный сервер), fallback сделан универсально: LM Studio (как
и Ollama, llama-server) уже поднимает OpenAI-совместимый HTTP-сервер -
ровно тот же протокол, которым `llm_client.py` и так пользуется для
облака. Поэтому переключение "облако -> локальная модель" - это просто
ВТОРОЙ `OpenAI`-клиент с другим `base_url`/`model`, без нового кода
протокола.

**Важная оговорка сразу, без неё оверселл:** это работает, только если
локальный сервер РЕАЛЬНО достижим с машины, где крутится `server.py`, по
сети - если LM Studio на отдельном Windows-компьютере, `base_url` должен
быть его LAN-адресом, а не `localhost` (`localhost` был бы адресом самого
Mint-компьютера). Если это дуалбут ОДНОЙ машины - fallback работать не
будет, пока Джарвис и LM Studio буквально не запущены одновременно на
разных ОС, что физически невозможно на одном железе без второй машины.
Это решается только на стороне сети/железа юзера, не кодом.

**Два способа переключения (оба сделаны, как и просили):**

1. **Автоматически** - облачный запрос не прошёл (нет сети, таймаут,
   ошибка API) -> пробуем локальный, если настроен, прежде чем сдаться.
2. **Вручную голосом** - "перейди в офлайн" / "перейди в онлайн" -
   мгновенная команда через `intent_router` (не через LLM - в духе
   "уверен или не лезу": офлайн/онлайн - однозначные бытовые слова, как
   "громче"/"тише"). В форсированном офлайн-режиме облако вообще не
   пробуется - незачем ждать таймаут заведомо не нужного запроса.

**`agents/llm_client.py`** - `create_fallback_client()`: как и
`create_client()`, но НИЧЕГО не обязательно - без `LLM_FALLBACK_BASE_URL`/
`_MODEL` возвращает `None`, и всё работает ровно как до этого раунда
(единственный провайдер, единственная ошибка при недоступности). API-ключ
необязателен - большинство локальных серверов его не проверяют вообще.

**`agents/llm_mode.py`** (новый) - общий флаг форсированного офлайн-режима
между `intent_router` (переключает) и `dialog_manager` (читает перед
каждым запросом). Вынесен в отдельный модуль СПЕЦИАЛЬНО: `intent_router`
по дизайну (раунд 12) не знает про `dialog_manager`/LLM вообще - и это
должно было остаться так же и после этого раунда.

**`agents/intent_router.py`** - новый матчер `_match_llm_mode()`:
"офлайн"/"оффлайн" (оба написания) и "онлайн" - без доп. контекстных слов,
как и "громче"/"тише" (слова достаточно однозначны в бытовой речи для
голосового ассистента).

**`agents/dialog_manager.py`** - `_create_stream()`: пробует облако,
кроме случая форсированного офлайна (тогда сразу локальный fallback, если
есть); при неудаче облака (и наличии fallback) - пробует локальный;
единственная ошибка - только если ВСЁ доступное не сработало. Сообщение
об ошибке разное в зависимости от того, настроен ли fallback вообще
(если нет - слово в слово то же, что было ДО раунда 23 - регрессия
проверена тестом).

**Что осознанно НЕ входит:** это НЕ автоматическая настройка/установка
локального рантайма - предполагается, что у юзера он уже есть (LM
Studio/Ollama/llama-server, любой). Также не проверяется заранее, умеет
ли конкретная локальная модель в function calling (`tools`) - если не
умеет, вызов к ней сам вернёт ошибку, и сработает та же ветка "оба не
сработали" - не идеальный UX, но не крэш и не тишина.

Проверено `test_llm_fallback.py` (13 тестов): `create_fallback_client()`
(None без обеих переменных, None при частичной настройке, клиент при
полной), голосовое переключение туда-обратно + альтернативное написание
"оффлайн", облако-успех никогда не трогает fallback, облако-неудача уходит
на fallback и получает ответ, облако-неудача БЕЗ настроенного fallback -
старое поведение один в один (регрессия), оба провалились - комбинированная
ошибка, форсированный офлайн вообще не трогает облако (`call_count == 0`),
форсированный офлайн без fallback не падает, а даёт понятную ошибку.

Полная регрессия после этого раунда - 80 тестов, все зелёные.

# Раунд 24: C5 - AT-SPI (чтение экрана, клик, ввод текста)

Из чек-листа C5 - "accessibility-слой (AT-SPI) вместо голого
shell-whitelist". До этого раунда `apps.py`/`folders.py` умели только
ЗАПУСКАТЬ вещи из белого списка - AT-SPI открывает гораздо более широкую
дверь: чтение содержимого произвольного окна и клики/ввод текста в его
элементы. Обсудили риски заранее (см. переписку) - два принципиально
разных источника опасности:

1. **Утечка контента в облако.** Всё, что возвращает любой tool, попадает
   в историю диалога и летит в облачный LLM как контекст. Если инструмент
   читает произвольное окно - туда попадёт всё, что там написано, вплоть
   до паролей и переписки.
2. **Непрямая prompt injection.** Если модель может и читать экран, и
   кликать - текст на экране (веб-страница, письмо) теоретически может
   содержать спрятанную инструкцию, которую модель попытается выполнить.

**Главное архитектурное решение раунда - не просто "добавить
подтверждение", а структурно закрыть риск №1:** три новых инструмента
(`atspi_read_active_window`, `atspi_click_element`, `atspi_type_text`,
`agents/tools/atspi_control.py`) **доступны ТОЛЬКО когда LLM-запрос
обслуживается локально** (форсированный офлайн-режим раунда 23 или
автоматический fallback) - облачная модель их вообще не видит, а не
"проинструктирована не использовать":

- `agents/tools/__init__.py` - модуль инструментов может опционально
  объявить `LOCAL_ONLY_TOOLS` (set имён), автозагрузчик собирает их из
  всех модулей в `agents.tools.LOCAL_ONLY_TOOLS`.
- `dialog_manager._create_stream()` - облачному провайдеру отправляется
  УРЕЗАННЫЙ список инструментов (без всего из `LOCAL_ONLY_TOOLS`),
  локальному/fallback - полный.
- `dialog_manager._execute_tool_call(is_local=...)` - ВТОРОЙ, защитный
  слой: отказывает в выполнении local-only инструмента, даже если он
  почему-то был запрошен во время облачного хопа (некоторые провайдеры
  пропускают "галлюцинированные" вызовы вне присланного списка).

Риск №2 (непрямая инъекция) этим НЕ закрыт полностью - и не может быть
закрыт одним архитектурным решением. Смягчается тем, что **все три
инструмента, включая ЧТЕНИЕ**, добавлены в `DANGEROUS_TOOLS`
(`agents/confirmation.py`, механизм C3, раунд 17) - голосовое
подтверждение перед КАЖДЫМ вызовом, без исключений. Читать тоже
подтверждаем - раз оно всё равно не идёт в облако, лишнее "да" не мешает,
а единое правило "здесь подтверждаем всегда" проще и безопаснее, чем
решать на лету, какое конкретно чтение "достаточно безобидно".

**Реализация** (`agents/tools/atspi_control.py`): обход дерева доступных
элементов активного окна через `gi.repository.Atspi` (Linux accessibility
API - та же шина, которой пользуются экранные дикторы), с ограничениями
`MAX_TREE_DEPTH`/`MAX_ELEMENTS`, чтобы сложное окно (IDE с деревом файлов)
не отдало тысячи строк в контекст локальной модели. Клик/ввод текста ищут
элемент нечётким совпадением по названию (тот же `fuzzy_lookup`, что и в
`apps.py`) и отказываются действовать при низкой уверенности - "уверен
или не лезу" (раунд 12) применён и здесь. Linux-only - AT-SPI специфичен
для Linux, аналог для Windows (UI Automation через `pywin32`) в этот
раунд не входит. Импорт `gi`/`Atspi` ЛЕНИВЫЙ (внутри функций, не на
уровне модуля) - если системных пакетов (`gir1.2-atspi-2.0`,
`python3-gi`) нет, каждый вызов возвращает понятную ошибку с подсказкой,
а не роняет автозагрузчик всех инструментов разом.

**Честно, без приукрашивания: НЕ проверено на реальной системе.** AT-SPI
требует живую графическую сессию с шиной accessibility, которой нет в
песочнице разработки - в отличие от раунда 22 (C++ PhraseSender), где
код был реально скомпилирован и прогнан живьём, здесь весь код написан
по документации GI-биндингов `Atspi` и покрыт тестами на ПОЛНОСТЬЮ
фейковой реализации этого API (`test_atspi_control.py`) - имена
методов/сигнатуры вполне могут потребовать мелкой правки при первом
реальном запуске на Mint. Системные пакеты, если ещё не стоят:
`sudo apt install gir1.2-atspi-2.0 python3-gi` (плюс убедиться, что
accessibility включена в самой системе - на GNOME/Cinnamon обычно
через `gsettings set org.gnome.desktop.interface toolkit-accessibility true`).

Проверено `test_atspi_control.py` (12 тестов, фейковый `Atspi`): обход
дерева и вывод подписей/текста, "активное окно не найдено", AT-SPI
недоступен (нет пакетов) -> понятная ошибка, а не исключение, Windows ->
отказ, ограничение `MAX_ELEMENTS` реально останавливает обход, клик/ввод
текста при уверенном совпадении срабатывают, при низкой уверенности - НЕ
срабатывают (элемент не тронут), элемент без доступных действий не
кликается, имена в `TOOL_SCHEMAS`/`TOOL_IMPLEMENTATIONS`/`LOCAL_ONLY_TOOLS`
согласованы. Плюс `test_cloud_local_tool_split.py` (5 тестов): облачный
запрос реально не содержит local-only схем, fallback-запрос содержит,
прямой вызов local-only инструмента с `is_local=False` отказывается
выполняться и не доходит до подтверждения, с `is_local=True` - доходит до
обычного C3-подтверждения, обычные (не local-only) инструменты не
затронуты флагом `is_local` (регрессия).

Полная регрессия после этого раунда - 97 тестов, все зелёные.

# Раунд 25: C6 - персистентные таймеры/напоминания

Из чек-листа C6 - "персистентные таймеры/напоминания (сейчас fire-and-forget,
пропадают при рестарте)". До этого раунда `set_timer` (`agents/tools/timers.py`)
был чистым `threading.Timer` в памяти процесса - никакого следа на диске.
Это уже было некрасиво само по себе, а после раунда 19 (watchdog в
`scripts/start.sh`, который перезапускает ВСЕ ТРИ процесса при падении
любого) стало по-настоящему проблемой: любой сбой сервера (сетевая ошибка
Whisper, что угодно) молча стирал все ожидающие таймеры без единого следа.

**Что сделано.** Каждый таймер при постановке (`set_timer()`) сразу
пишется в `data/timers.json` с АБСОЛЮТНЫМ временем срабатывания
(`fire_at_unix = time.time() + seconds`, не "осталось секунд" - так
переживает любое число перезапусков без пересчёта на каждом шаге) и
стирается оттуда, когда реально сработал. Новая функция
`load_pending_timers()` вызывается `server.py` один раз при старте, СРАЗУ
после `register_timer_notifier()` (порядок важен - иначе просроченному
таймеру, который сработает почти сразу, некому будет позвонить):
перечитывает файл и перепланирует всё, что там сохранено.

**Ключевая деталь - что делать с таймерами, чьё время УЖЕ прошло, пока
процесс не работал.** Они срабатывают немедленно при загрузке - но с
пометкой в самом сообщении ("(таймер, поставленный до перезапуска) ...")
- иначе было бы совершенно непонятно, почему Джарвис вдруг заговорил сам
через долю секунды после запуска. Таймеры, чьё время ЕЩЁ не прошло,
срабатывают в свой обычный срок без всякой пометки - это неотличимо для
пользователя от таймера, поставленного в этой же сессии, и пометка там
была бы просто шумом.

Битый или недоступный `data/timers.json` (повреждённый файл, права
доступа) не роняет запуск сервера - `_load_all()` просто считает, что
сохранённых таймеров нет, и печатает предупреждение в лог.

Проверено `test_timer_persistence.py` (12 тестов, путь к файлу состояния
подменяется на временный - реальный `data/timers.json` проекта не
трогается, ожидание срабатывания - через `threading.Event` с таймаутом,
не голый `sleep`, чтобы тест не флейкал): постановка пишет на диск с
правильным будущим временем, несколько таймеров хранятся независимо,
сработавший таймер удаляется с диска, восстановление ещё-не-просроченного
таймера срабатывает БЕЗ пометки в свой обычный срок, восстановление
просроченного - НЕМЕДЛЕННО и С пометкой, отсутствующий/битый/не-словарный
файл не роняет `load_pending_timers()` (возвращает 0), отсутствие
зарегистрированного notifier'а не роняет срабатывание.

Полная регрессия после этого раунда - 109 тестов, все зелёные.

# Раунд 26: C7 - долгосрочная память вне истории диалога

Из чек-листа C7 - "долгосрочная память (факты о юзере, проекты) вне
LLM-истории". До этого раунда единственная "память" Джарвиса -
`dialog_manager._history` - хранит последние `HISTORY_MAX_TURNS` (8) ходов
и **полностью обнуляется** при перезапуске процесса (`self._history = []`
при старте, раунд 11, - осознанно, чтобы не тянуть обрывок случайного
старого диалога после падения). Значит, ничего сказанное в прошлой сессии
("меня зовут Артём", "я работаю над Джарвисом") не переживало даже один
перезапуск, не говоря уже о конце конкретного разговора.

**Два новых инструмента** (`agents/tools/memory.py`):
- `remember_fact(text)` - сохраняет короткий факт в `data/memory.json`
  (тот же паттерн персистентности, что и у таймеров - раунд 25, но
  отдельный файл, отдельная сущность);
- `forget_fact(text_hint)` - удаляет факт по нечёткому совпадению с
  подсказкой.

**Ключевое отличие от истории:** факты не сидят в `self._history` и не
участвуют в откате/лимите ходов - `dialog_manager._build_system_prompt()`
подмешивает их отдельным блоком в СИСТЕМНЫЙ промпт на КАЖДЫЙ запрос
(`load_facts_summary()`, реэкспортирована из `tools/__init__.py` как
специальный случай, аналогично `register_timer_notifier`/
`load_pending_timers` в раунде 25). Если фактов нет - промпт не
отличается от того, что было до этого раунда, ни на символ (проверено
тестом).

**НЕ помечено local-only** (в отличие от AT-SPI, раунд 24) - и это
осознанно, не недосмотр: факты и так предназначены для того, чтобы модель
их использовала в ответах, а вся история диалога и так уже целиком уходит
в облако - отдельного нового риска утечки они не создают.

**НЕ требуют голосового подтверждения** (в отличие от `lock_computer`/
AT-SPI, C3/C5) - запись или удаление текстовой заметки не разрушительна и
легко обратима (`forget_fact` в одну сторону, `remember_fact` в другую).
Постоянно переспрашивать "точно запомнить X?" сделало бы фичу неудобной
до бесполезности - соразмерность трения риску, а не рефлекс "раз можем
спросить - спросим".

**Решение "запоминать или нет" оставлено самой модели**, а не жёсткому
списку триггер-слов, как в `intent_router.py` - осознанная асимметрия:
там неверное решение - это ошибочно выполненное ДЕЙСТВИЕ мимо LLM (дорогая
ошибка), здесь - лишняя строчка в файле с фактами (дешёвая, поправимая
через `forget_fact`).

**Техническая деталь про нечёткий поиск в `forget_fact`:** обычный
`fuzzy_lookup()` из `_shared.py` (`fuzz.ratio` - сравнение строк ЦЕЛИКОМ)
тут не годится - пользователь называет короткое ключевое слово
("Джарвис"), а не всю фразу факта целиком ("Артём работает над
Джарвисом"); `fuzz.ratio` штрафует за разницу в длине и дал бы низкий
скор даже для точного вхождения. Вместо этого `forget_fact` использует
`fuzz.partial_ratio` напрямую - ищет наилучшее совпадение ПОДСТРОКИ, что
и нужно для этого случая. Порог (70) подобран под другой scorer, не
совпадает с порогами `fuzzy_lookup()` в других файлах - не путать при
переиспользовании.

Как и `set_timer` (раунд 25), список фактов ограничен
(`MAX_REMEMBERED_FACTS = 50`, FIFO - старые вытесняются новыми, не отказ)
- иначе промпт рос бы бесконечно с каждым новым фактом и раздувал бы
каждый последующий запрос.

Проверено `test_memory_persistence.py` (15 тестов, путь к файлу состояния
подменяется на временный): запись на диск, отклонение пустого/слишком
длинного факта, несколько фактов хранятся независимо, FIFO-вытеснение при
переполнении реально вытесняет САМЫЕ старые, `forget_fact` удаляет
уверенно совпавший факт и НЕ трогает память при низкой уверенности,
пустая/отсутствующая/битая память не роняет вызовы. Плюс интеграционные
тесты с `dialog_manager` (переиспользуют `CapturingClient` из раунда 24):
системный промпт **не меняется вовсе**, если фактов нет (регрессия слово
в слово), и **реально содержит** запомненный факт, если он есть, поверх
исходного текста промпта, а не вместо него.

Полная регрессия после этого раунда - 124 теста, все зелёные.

# Раунд 27: E1 - словарь исправлений STT + "лог трения"

Из чек-листа E1 - "словарь типичных ошибок STT ('темножить'→'умножить')".
В обсуждении всплыла смежная идея - "чтобы Джарвис сам понимал, где
накосячил" - разобрали на составные части, не стали делать одним куском:

**"Запоминать что-то важное"** - это уже C7 (раунд 26, `remember_fact`) -
отдельная задача не нужна, она уже закрыта.

**"Сам понимал и сам себя правил" - НЕ сделано, осознанно.** Надёжно
определить программно "здесь была ошибка STT, а не баг/странная фраза
пользователя" - трудно, и система, которая сама решает, что была
неправа, и сама правит свой же словарь замен, может с тем же успехом
убедить себя, что была неправа там, где была права - тихая порча
словаря без контроля юзера. Вместо самокоррекции - две отдельные,
более скромные и предсказуемые вещи:

**1. `framework/stt_corrections.py` + `config/stt_corrections.yaml`** -
классический словарь замен. Применяется в `server.py`
(`transcribe_worker`) СРАЗУ после Whisper, ДО intent_router/confirmation/
LLM - весь код ниже видит уже исправленный текст, ничего специально про
STT-ошибки не знает. Замена - по границе слова (`\b`), без учёта
регистра, не голая подстрока (иначе короткое правило могло случайно
задеть кусок более длинного слова). **Hot-reload по mtime файла** - можно
редактировать `config/stt_corrections.yaml` прямо во время работы
сервера, правило заработает на следующей же фразе, перезапуск не нужен
(дешёвый `stat()` на каждый вызов, полное перечитывание - только когда
файл реально поменялся).

**2. `framework/gap_log.py` - "лог трения", НЕ автокоррекция.** Каждый
значимый затык - LLM недоступна целиком (ни облако, ни локальный
fallback), инструмент упал с НЕПРЕДВИДЕННЫМ исключением (не обычный
`{"error": ...}`, который инструмент вернул сам, а реальный краш
реализации), агент уткнулся в лимит шагов (`MAX_TOOL_HOPS`) и сдался -
одна строка в `data/gaps.jsonl` (`kind`/`detail`/`user_text`/`ts`). Юзер
сам потом читает и решает: словарная замена сюда же в `stt_corrections.yaml`,
баг, недостающий tool - тот же паттерн, что и в раундах 3/6 ("фикс по
логам с реального теста"), просто автоматизированный и постоянный, а не
разовый ручной сбор через чат. Формат - JSONL, можно `tail -f` смотреть
вживую. Ограничен по размеру (`MAX_GAP_LOG_ENTRIES = 500`, FIFO - тот же
принцип, что у `memory.py`, раунд 26) - диагностический журнал для юзера,
не архив на вечное хранение.

Три точки в `dialog_manager.py`, где реально вызывается `log_gap()`:
`_create_stream()` полностью провалился (и облако, и fallback, если был),
`_execute_tool_call()` поймал непредвиденное исключение из tool'а, и
фолбэк-ветка после исчерпания `MAX_TOOL_HOPS`. Обычные ожидаемые
"отказы" (например, `forget_fact` не уверен, какой факт забыть, или C3
попросил подтверждение) - это НЕ затыки, а система работает как задумано
- в лог не попадают, иначе журнал захламился бы шумом и потерял ценность
как источник РЕАЛЬНЫХ проблем.

Проверено `test_stt_corrections.py` (10 тестов): замена срабатывает и
регистронезависимо, граница слова не задевает случайно похожие более
длинные слова, пустой текст/отсутствующий/битый/не-словарный YAML не
роняют вызов, несколько правил применяются независимо, **hot-reload
реально подхватывает изменения файла без перезапуска процесса**. Плюс
`test_gap_log.py` (8 тестов: запись/несколько записей по порядку/FIFO-
вытеснение при переполнении/чтение последних N/битые строки не роняют
чтение/недоступная директория не роняет запись) и
`test_gap_log_integration.py` (4 теста, поверх реального
`dialog_manager` с фейковым LLM-клиентом): все три точки трения реально
пишут запись правильного вида, а обычный успешный вызов НЕ пишет ничего
(регрессия против "лог захламляется на пустом месте").

Полная регрессия после этого раунда - 146 тестов, все зелёные.

# Раунд 28: E2 - история диалога на диск + резюме старых ходов

Из чек-листа E2 - "история диалога на диск + summary старых ходов
(сейчас fire-and-forget, пропадают при рестарте)". Уточнение важно:
`self._history` в `dialog_manager.py` **осознанно** обнуляется при
перезапуске процесса (раунд 11 - "не тянуть обрывок случайного старого
диалога после падения") - этот раунд НЕ меняет то решение и не пытается
восстанавливать дословную историю через рестарт. Две другие, более узкие
вещи, которые реально просил чек-лист:

**1. `framework/conversation_log.py` - полный транскрипт на диск.**
Каждое сообщение (user/assistant/tool), попадающее в `self._history`,
теперь ЕЩЁ И дописывается в `data/conversation_log.jsonl` через новый
единый метод `DialogManager._append_history()` (заменил 4 отдельных места
с `self._history.append(...)` - централизует логирование, чтобы будущие
новые точки добавления в историю не забыли про запись на диск). Это
ЧИСТО дневник для юзера - НИКОГДА не читается обратно в код, не влияет
ни на что в работе Джарвиса, не participates в запросах к LLM. Формат и
защита от бесконечного роста - тот же паттерн, что и в `gap_log.py`
(раунд 27): JSONL, FIFO-вытеснение при переполнении
(`MAX_CONVERSATION_LOG_ENTRIES = 5000`).

**2. Резюме выпадающих реплик (`DialogManager._update_summary()`).** До
этого раунда `_trim_history()` при превышении `HISTORY_MAX_TURNS` просто
ВЫБРАСЫВАЛ старые ходы без следа. Теперь выпадающие реплики сжимаются
отдельным маленьким LLM-вызовом (без инструментов, без остального
контекста) в 2-4 предложения и объединяются с уже накопленным
`self._history_summary` в одно обновлённое резюме - не цепочка резюме
одно поверх другого. `_build_system_prompt()` (раунд 26, C7) подмешивает
это резюме ВТОРЫМ отдельным блоком, рядом с долгосрочными фактами, но с
чёткой разницей: факты - это про пользователя НАВСЕГДА, резюме - про то,
что уже обсуждали В ЭТОМ разговоре, но что не помещается в живое окно
дословной истории. Резюме, как и вся история, НЕ переживает перезапуск -
тот же принцип round 11.

**Выбор клиента для резюмирования (`_pick_summary_client()`)** - тот же
`llm_mode.is_forced_offline()`, что и для основных ответов (B6, раунд
23), но **БЕЗ** автоматического фолбэка при сбое, в отличие от
`_create_stream()`: это вспомогательная, необязательная функция - если
выбранный вариант не сработал, резюме просто не обновляется в этот раз
(выпавшие реплики теряются молча, ОДИН раз, до следующей попытки), не
стоит того, чтобы дублировать всю retry-логику ради второстепенной фичи.
Сбой пишется в лог трения (`gap_log`, раунд 27, `kind="summary_failed"`) -
видимость для юзера, не тихая деградация совсем без следа.

Проверено `test_conversation_log.py` (6 тестов, тот же паттерн, что и
`test_gap_log.py`): запись/порядок/FIFO-вытеснение/недоступная директория
не роняет запись. Плюс `test_history_summary.py` (13 тестов): системный
промпт не меняется без резюме (регрессия), реально включает резюме, если
оно есть, `_update_summary()` реально вызывает LLM и сохраняет результат,
включает ПРЕДЫДУЩЕЕ резюме в промпт следующего вызова (не теряет
накопленное), сбой вызова оставляет старое резюме как было и пишет в
gap_log, реплика без текстового content (чистый tool_call) не роняет
сборку текста для запроса, выбор клиента корректен в обычном режиме/
форсированном офлайне/форсированном офлайне без fallback,
`_trim_history()` реально вызывает суммаризацию только когда реально
превышен лимит (не раньше), и сквозной прогон через `handle()` на
`HISTORY_MAX_TURNS + 2` ходов - резюме реально появляется и реально
долетает до системного промпта следующего запроса, плюс что сообщения
реально долетают до `conversation_log.jsonl` через настоящий вызов
`handle()`, а не только напрямую.

Полная регрессия после этого раунда - 164 теста, все зелёные.

# Раунд 29: E3 - "мультиагент" (рутина локально / тяжёлое в облако)

Из чек-листа E3 - "мультиагент (рутина локально / тяжёлое → внешний
LLM)". Последний пункт исходного чек-листа - группа E закрыта целиком.

**До этого раунда (B6, раунд 23) направление было ровно одно: облако
ВСЕГДА первым, локальный fallback - только при сбое или в форсированном
офлайн-режиме.** E3 - не новый механизм, а НОВОЕ ПРАВИЛО ВЫБОРА порядка
для уже существующей пары клиентов: если fallback настроен и запрос
похож на рутину - пробуем ЛОКАЛЬНО первым.

**Критерий "рутина или тяжёлое" - обсудили заранее, а не выдумали.** Три
варианта на выбор: по длине фразы, по тому, нужны ли инструменты вообще,
или отдельный LLM-вызов "разведчик" перед основным. Юзер выбрал первый -
"по сложности, чтобы долго не думал". `_is_routine_query()`
(`dialog_manager.py`) - длина фразы в словах, порог настраивается
(`config.yaml`, `multi_agent.routine_max_words`, по умолчанию 8). Ничего
умнее специально не делали - список триггер-слов "сложности" был бы
хрупким и непрозрачным, а отдельный LLM-вызов ради решения "звать ли
LLM" бессмысленен по построению.

**`_create_stream()` - новая ветка ПЕРЕД существующей облако-первым
логикой:** если fallback настроен, не форсированный офлайн, и запрос
рутинный - пробуем `self._fallback_client` первым. Если он ответил (даже
плохо) - принимаем ответ как есть, **НЕ судим качество** (это был бы ещё
один LLM-вызов, что противоречило бы самой цели "не думать долго"). Если
локальный вызов реально не сработал ТЕХНИЧЕСКИ (сеть/модель недоступна) -
падаем в обычную ветку "облако первым" ниже, точно так же, как облако
эскалирует в fallback при сбое (симметрично).

**Если fallback не настроен - E3 не меняет ничего**, ни для рутины, ни
для тяжёлого - поведение идентично раунду 23 один в один (проверено
регрессией). Это ключевое свойство: юзер без настроенной локальной модели
вообще не заметит этот раунд.

**Побочный эффект на тесты раунда 23:** три теста в `test_llm_fallback.py`
(`test_cloud_success_never_touches_fallback` и парные) использовали
однословное `"Привет"` как тестовое сообщение - с фейковым fallback,
настроенным В ТЕХ тестах, короткая фраза теперь попадала под эвристику
"рутина" и уходила в fallback ПЕРВЫМ, что ломало сам смысл тех тестов
(проверить именно облако-первым поведение B6). Поправлено - сообщение в
этих трёх тестах теперь длиннее 8 слов, с комментарием почему. Хороший
пример, почему регрессия гоняется целиком после каждого изменения, а не
только новые тесты - это не баг в новом коде, а честное взаимодействие
между раундами.

Проверено `test_multi_agent_routing.py` (11 тестов): эвристика (граница
ровно на пороге, порог настраивается через `config.yaml`), рутинный
запрос реально уходит в локалку первым при настроенном fallback
(облако вообще не тронуто), тяжёлый запрос - по-прежнему в облако,
рутинный без настроенного fallback - в облако как раньше (регрессия),
рутинный запрос эскалирует в облако, если локалка реально недоступна,
форсированный офлайн (B6) полностью игнорирует эту эвристику (уже и так
безусловно идёт в fallback), и что маршрутизация "рутина -> локально"
корректно помечается как `used_fallback=True` для защиты C5
(LOCAL_ONLY_TOOLS) - не ломает существующий защитный механизм.

Полная регрессия после этого раунда - 175 тестов, все зелёные.

**Чек-лист E закрыт целиком** (E1 - раунд 27, E2 - раунд 28, E3 - этот
раунд). Группы A, B, C, E - все закрыты. Из исходного списка "что
осталось" открыт только D2-D4 (реальный full-duplex АЕС - железо/ядро,
самое крупное и не начатое) и обученная под русский wake-word-модель
(раунд 14 - механика готова, модели нет).

## Альтернатива шагу 3 (раунд 19): один скрипт вместо трёх терминалов

После сборки ядра (шаг 1) и установки зависимостей (шаг 2) можно вместо
ручного запуска в трёх терминалах поднять всё разом:

```bash
./scripts/start.sh
```

Сам следит за тем, что все три процесса живы, и перезапускает всё разом
при падении любого - подробности и обоснование см. "Раунд 19" выше.
Остановка - `Ctrl+C` в этом же терминале либо `./scripts/stop.sh` из
другого. Автозапуск при логине - `deploy/systemd/jarvis.service` (там же
инструкция по установке).

Логи каждого процесса - `logs/{server,core,ui,watchdog}.log`, ротируются
автоматически при достижении `JARVIS_LOG_MAX_BYTES` (по умолчанию 5 МиБ),
хранится до `JARVIS_LOG_BACKUPS` архивов (по умолчанию 5) - см. "Раунд 20".

## Альтернатива россыпи export'ов (раунд 21): config.yaml + .env

Все `export WHISPER_MODEL_SIZE=...`/`export PIPER_MODEL_PATH=...`/и т.п.
из инструкций выше по-прежнему работают один в один - ничего не сломано.
Но если не хочется держать их в `~/.bashrc`, можно вместо этого:

```bash
cp .env.example .env
nano .env   # вписать LLM_API_KEY (обязательно) и, если нужно, JARVIS_BACKEND_API_KEY
nano config/config.yaml   # несекретные настройки - модель Whisper, голос Piper и т.п.
```

Секреты - только в `.env` (в git не идёт). Всё остальное - в
`config/config.yaml` (можно спокойно класть в git). Подробности и порядок
приоритета - см. "Раунд 21" выше. `WAKEWORD_*` (C++ ядро) и переменные
`scripts/start.sh` сюда не входят - для них по-прежнему только `export`.

Локальный fallback без интернета (раунд 23, B6) - `config/config.yaml`,
секция `llm_fallback:` (`base_url`/`model`), пусто по умолчанию = выключен.
Голосом переключается командой "перейди в офлайн"/"перейди в онлайн".

Словарь исправлений STT (раунд 27, E1) - `config/stt_corrections.yaml`,
редактируется на ходу, перезапуск не нужен (hot-reload по mtime файла).
Смотреть, что чинить, - `data/gaps.jsonl` ("лог трения", тот же раунд):
каждый значимый затык (LLM недоступна, инструмент упал, агент сдался за
`MAX_TOOL_HOPS` шагов) - одна строка, `tail -f data/gaps.jsonl` для
просмотра вживую.

Полный транскрипт разговора (раунд 28, E2) - `data/conversation_log.jsonl`,
чисто для чтения человеком, ни на что в работе Джарвиса не влияет
(отдельно от живой истории диалога, которая обнуляется при перезапуске -
осознанно, раунд 11).

Если микрофон реально очень тихий (Amp в статус-баре почти всегда < 100 даже
во время речи) — это уже не код, а настройки записи в ОС: проверьте уровень
входного сигнала в `alsamixer` / `pavucontrol`, возможно, физически поднят
на минимум или выбрано не то устройство по умолчанию.
