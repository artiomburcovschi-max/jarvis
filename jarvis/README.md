# Jarvis — что было исправлено

## 1. Главный баг: VAD не видел речь (SileroVAD.cpp / .h)

Модель `silero_vad.onnx` — это Silero VAD v5. Официальная реализация подаёт
на вход не 512 сэмплов, а **576 = 64 (контекст от предыдущего кадра) + 512
(новый кадр)**. Старый код кормил модель голыми 512 сэмплами без контекста.
Модель не падала (входной тензор объявлен с динамической формой), но
вероятность речи почти никогда не поднималась выше 0.1–0.15 — то есть порог
`VAD_SPEECH_THRESHOLD = 0.55` не пробивался почти никогда, даже на громкой
чистой речи.

Проверено на скомпилированном коде: на тестовой фразе `max_prob` было
`0.114` (без контекста) против `0.9999` (с контекстом).

Исправлено в `core/include/SileroVAD.h` и `core/src/SileroVAD.cpp`.

## 2. RUNPATH был захардкожен на машину сборки

Бинарник помнил абсолютный путь `/home/.../onnxruntime.../lib`, из-за чего
при переносе/переименовании папки переставал находить `libonnxruntime.so`.
Теперь путь в `core/CMakeLists.txt` задан через `$ORIGIN` — переезжает
вместе с папкой проекта.

## 3. Запись микрофона могла тормозиться сетью (main.cpp)

Раньше `zmq_socket.send()` вызывался прямо в цикле чтения микрофона. Если
Python был занят распознаванием предыдущей фразы, а пользователь уже
начинал новую (перебивание), при заполнении внутренней очереди ZMQ `send()`
мог заблокироваться — и мы бы теряли аудио. Теперь отправка вынесена в
отдельный поток (`core/include/PhraseSender.h`) с очередью: запись с
микрофона никогда не ждёт сеть.

## 4. Начало фразы обрезалось (main.cpp)

VAD распознаёт речь не мгновенно — ему нужно 2–3 кадра (60–90 мс), чтобы
"разогнаться" выше порога. Раньше запись фразы начиналась только с кадра,
на котором сработал VAD, и начало слова "Джарвис" часто терялось. Добавлен
pre-roll буфер (~320 мс, кольцевой), который приклеивается к фразе в момент
срабатывания VAD.

## 5. Защита от зависшей фразы

Если VAD ложно держится "в речи" (шум, гул) — раньше буфер рос бы вечно.
Теперь есть `MAX_PHRASE_SAMPLES` (15 сек) — по достижении фраза
принудительно уходит на распознавание, а запись продолжается как ни в чём
не бывало (это же покрывает и сценарий, когда человек говорит длинно без
пауз, перебивая сам себя).

## 6. Python-сервер падал целиком при ошибке на одной фразе (server.py)

Раньше весь `try/except` был вокруг всего цикла — одна битая фраза
(например, если Whisper споткнулся) убивала сервер, и дальше он вообще
переставал что-либо принимать. Теперь приём аудио (`socket_audio.recv()`) и
распознавание (Whisper) разнесены на два потока через `queue.Queue`, и
ошибка на одной фразе не мешает обработке следующих.

## 7. "Диалоговое окно" — не нужно повторять "Джарвис" каждый раз

После того как сказано слово-активатор, в течение 10 секунд (см.
`ACTIVE_WINDOW_SECONDS` в `server.py`) следующие фразы считаются командами
без повторного "Джарвис" — как у обычных голосовых ассистентов. Это и есть
базовая обработка "перебивания"/продолжения диалога.

## 8. requirements.txt был неполным

Не хватало `faster-whisper`, `rapidfuzz`, `PySide6` — только `pyzmq`.
Исправлено.

# Раунд 2: закрытые сценарии из чек-листа (акустика/железо/сессии)

Список сценариев был разобран на 3 корзины: (1) чинится на уровне
VAD/STT/сессий, (2) принципиально требует LLM/NLU, (3) требует железа
(TTS+AEC, второе устройство). Ниже — что сделано по корзине (1), с проверкой
на реально скомпилированном коде и живым end-to-end тестом (python-клиент,
эмулирующий протокол C++ ядра → server.py → UI-сокет).

- **Импульсный шум / щелчок (хлопок двери, лай, щелчок аппаратуры)** —
  `main.cpp`: добавлен антидребезг открытия фразы (`CONFIRM_FRAMES = 2`,
  ~64мс). Одиночный кадр с высокой вероятностью речи больше не открывает
  фразу — нужно 2 кадра подряд. Начало реальной речи по-прежнему не
  обрезается благодаря pre-roll буферу.
- **Галлюцинации тишины/шума в STT** — `server.py`: добавлен
  `is_hallucinated_segment()` — отсекает сегменты по `no_speech_prob`,
  `avg_logprob`, `compression_ratio` (штатные признаки "выдумывания" у
  Whisper). Проверено сценарием: шумовая фраза с плохими метриками
  корректно не долетает до UI.
- **"Зависла STT, ответ пришёл после того как сессия уже закрылась по
  таймауту"** — раньше диалоговое окно проверялось по текущему времени
  (когда Whisper закончил), теперь — по времени, когда фраза реально была
  произнесена (`ts` в заголовке сообщения). Долгая обработка одной фразы
  больше не путает логику "продолжается диалог или нет".
- **Мышление вслух / долгая пауза с "эээ" в середине фразы** — уже
  работало (любой звук выше порога сбрасывает счётчик тишины), но hangover
  увеличен с ~0.8с до ~1.0с для небольшого запаса.
- **Тихий шёпот** — расширен диапазон авто-гейна (порог активации снижен
  со 100 до 50, потолок усиления поднят с 10x до 15x). Это не чинит
  физически "глухой" микрофон, но даёт больше шансов тихой речи.
- **Сетевая устойчивость / порядок фраз** — каждая фраза теперь уходит
  двумя zmq-фреймами: JSON-заголовок `{"seq", "ts"}` + сырые PCM16-байты.
  Это база для будущего сетевого сценария (не только localhost) и для
  честного лога задержки речь→текст.

Корзины (2) и (3) намеренно не тронуты — это LLM/NLU-слой (не построен
командой линии VAD-порогов) и железо (TTS+AEC, второе устройство), которых
в проекте пока физически нет.

# Раунд 3: повторный аудит (архитектура/баги)

По запросу "всё ли оптимально" — прошёлся по коду ещё раз пристрастно,
специально ища то, что сам мог упустить в спешке. Нашлось 4 реальные вещи:

1. **Дублирование кадра на стыке открытия фразы (main.cpp)** — при
   срабатывании антидребезга (раунд 2) preroll-буфер уже содержал текущий
   кадр, а следом он же добавлялся ещё раз общей веткой записи. На каждой
   фразе в начало записи попадали лишние ~32мс повторяющегося звука.
   Проверено отдельным тестом на симуляции состояний: раньше кадр
   дублировался бы, теперь каждый кадр входит в буфер ровно один раз.
2. **Неограниченный рост очереди в PhraseSender.h** — если Python-сервер
   долго недоступен (упал/не запущен), очередь на отправку росла бы
   бесконечно. Добавлен потолок в 50 фраз с вытеснением самых старых
   (свежая речь важнее устаревшего бэклога).
3. **CMakeLists.txt собирал без оптимизаций по умолчанию** — `cmake ..` без
   явного `-DCMAKE_BUILD_TYPE=Release` собирал в дефолтном (не оптимизированном)
   режиме. Теперь Release выставляется по умолчанию, если не указано иное.
4. **Двойная инициализация PortAudio (AudioRecorder.cpp)** — при
   использовании `deviceNameHint` (сейчас неактивный путь, т.к. `Start()`
   вызывается без аргументов) `Pa_Initialize()` вызывался дважды, а
   `Pa_Terminate()` в `Stop()` — один раз. Не проявлялось в текущем сценарии
   использования, но было заложенной миной на будущее. Исправлено.

Также зафиксированы (не исправлены — это либо косметика, либо territория
LLM-слоя, а не VAD/аудио):
- `strip_wake_word()` не отрежет имя, если STT склеил его с командой без
  пробела ("джарвисвыключисвет") — это уже вопрос сегментации слов, решается
  нормально только на уровне LLM/NLU, не VAD.
- Сообщение "[ZMQ] Успешно подключено!" при старте ядра технически означает
  только "сокет создан", а не "Python точно слушает" — `zmq_socket.connect()`
  всегда возвращает успех сразу же, реальное соединение асинхронное. На
  поведение это не влияет (ZMQ переподключается и буферизует сам), но как
  формулировка немного вводит в заблуждение.

# Этап 1: LLM-слой (Gemini + function calling)

Распознанный текст команды больше не уходит в UI как есть — сначала идёт в
`agents.DialogManager`, который обращается к Gemini с function calling, и уже
осмысленный ответ модели уходит в UI.

## Настройка

1. Получи бесплатный API-ключ на https://aistudio.google.com/apikey
2. Установи переменную окружения перед запуском `server.py`:
   ```bash
   export GEMINI_API_KEY="твой-ключ"
   ```
3. Если ключ не задан — сервер **не падает**, а печатает предупреждение и
   работает в режиме чистого STT-эхо (как на предыдущих этапах). LLM-слой —
   опциональная надстройка, а не обязательное условие запуска.

## Архитектура

- `framework/agents/tools.py` — инструменты (function calling). Это обычные
  Python-функции с type hints и docstring'ами: `get_current_datetime()` и
  `calculate(expression)`. SDK (`google-genai`) сам строит JSON-схему из
  сигнатуры функции и **сам выполняет вызов** (Automatic Function Calling) —
  ручного парсинга `function_call`/`function_response` не требуется, только
  передать функции в `config.tools`.
- `calculate()` намеренно не использует `eval()` — выражение приходит от
  LLM, которая реагирует на текст от пользователя, а `eval()` дал бы прямой
  путь к инъекции произвольного Python-кода через промпт. Вместо этого —
  разбор через `ast` с разрешённым белым списком операций. Проверено
  конкретными эксплойтами (`__import__(...)`, `open(...)`) — оба отбиваются.
- `framework/agents/dialog_manager.py` — `DialogManager.handle(text) -> str`.
  Хранит историю разговора, обрезает её сверху (`HISTORY_MAX_TURNS`), чтобы
  не раздувать контекст в длинном диалоге. `reset()` вызывается сервером,
  когда открывается новая сессия (сказано "Джарвис" после долгой паузы) —
  старый, не относящийся к делу контекст не тащится в новый разговор.
- При сетевой ошибке / таймауте / исчерпанной квоте `handle()` не бросает
  исключение — возвращает вежливый текст об ошибке и откатывает историю,
  чтобы не оставить в ней "оборванную" реплику без ответа.

## Модель и её будущее

Используется `gemini-2.5-flash` ($0.30/$2.50 за млн токенов вход/выход на
июль 2026). **Google планирует вывести её из эксплуатации 16 октября 2026** —
к этому моменту нужно будет поменять `DEFAULT_MODEL` в `dialog_manager.py` на
`gemini-3-flash` или `gemini-3.1-flash-lite`.

DeepSeek для тяжёлых/код-задач в этом этапе ещё не подключён (по плану —
следующий этап, как отдельный `delegate_to_deepseek`-инструмент). Важно на
будущее: легаси-имена `deepseek-chat`/`deepseek-reasoner` выводятся из
обращения 24 июля 2026 — актуальное имя модели в API теперь
`deepseek-v4-flash`.

## Что проверено (без реального обращения к Gemini — ключа и доступа к
`generativelanguage.googleapis.com` в песочнице нет, поэтому это mock-тесты
и одна честная оговорка):

- Реальный установленный `google-genai` SDK введён в код через интроспекцию
  (не по памяти) — сигнатуры `generate_content`, `Content`/`Part`/
  `FunctionCall`/`FunctionResponse`, механизм Automatic Function Calling и
  формат `automatic_function_calling_history` подтверждены чтением исходников
  самого пакета.
- `calculate()`/`get_current_datetime()` — юнит-тесты, включая 2 попытки
  инъекции кода (отбиты).
- `DialogManager` — мок-тест на подставном `genai.Client`: корректное
  накопление истории на 2 хода подряд, корректный `reset()`, корректный откат
  истории при симулированной сетевой ошибке.
- Полный путь целиком: фейковая фраза → `server.py` → заглушка Whisper →
  `DialogManager` (с моком Gemini, который решает вызвать `calculate`) →
  реальное выполнение инструмента → ответ в UI-сокете. Прогнано и с
  `GEMINI_API_KEY`, и явно без него (проверка graceful degradation).
- **Не проверено**: реальный сетевой вызов к Gemini API с настоящим ключом —
  это можно сделать только на твоей машине с реальным `GEMINI_API_KEY`,
  сеть до Google API в этой песочнице недоступна.

# Как собрать и запустить

```bash
# 1. Собрать C++ ядро
cd core
rm -rf build && mkdir build && cd build
cmake .. && make -j$(nproc)

# 2. Поставить python-зависимости (в venv)
cd ../../framework
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

# 3. Запустить (в трёх разных терминалах, именно в таком порядке)
python server.py          # сначала сервер - слушает порт 5555/5556
cd ../core/build && ./jarvis_core   # затем ядро - подключается к 5555
cd ../../framework && python main.py  # затем UI - подключается к 5556
```

Если микрофон реально очень тихий (Amp в статус-баре почти всегда < 100 даже
во время речи) — это уже не код, а настройки записи в ОС: проверьте уровень
входного сигнала в `alsamixer` / `pavucontrol`, возможно, физически поднят
на минимум или выбрано не то устройство по умолчанию.
